# 多副本部署（横向扩展）准备清单

> 适用版本：1.25.x ｜ 对应「B: 多副本准备」批次（限流/缓存 Redis 化、媒体临时目录可配、进程内单例盘点）。
> 结论先行：**代码层已就绪，默认行为仍是单实例**。不配置 `REDIS_URL`、不挂共享卷时直接多副本，会出现「限额按副本数放大 / 缓存短时不一致 / 分片上传偶发 404」。上线前请逐项勾选。

## 2. 仍需外部配置 / 决策

1. **Redis（可选，多副本强烈建议）**
   - `docker compose --profile redis up -d` 启动 `redis` 服务（只绑回环 `127.0.0.1:6379`，不持久化，`allkeys-lru` 128MB）；
   - 在 `.env` 设置 `REDIS_URL`：同一 compose 网络填 `redis://redis:6379`，app 跑在宿主机则 `redis://127.0.0.1:6379`；
   - 未配置 = 纯内存（与改造前**完全一致**）；配置但连不上 = 500ms 内降级内存并只打一条告警日志。
2. **限流调用点迁移（多副本共享限额的前提）**
   - 现有 **34 处**路由使用同步 `rateLimit()` / `checkLoginLock()` / `recordLoginFailure()`（进程内计数）；
   - 多副本下限额会被放大 N 倍（登录爆破/上传刷量可绕过）。共享化只需把调用点改成：
     `const r = await rateLimitShared(opts)`、`await checkLoginLockShared(key, opts)`、`await recordLoginFailureShared(...)`、`await clearLoginFailuresShared(...)`（`@/lib/infrastructure/rate-limit-factory`）；
   - 单实例部署不迁移也完全正确（未配 Redis 时 `*Shared` 与同步版等价）。
3. **媒体分片临时目录共享**：`MEDIA_TMP_DIR` 指向所有副本可见的卷（如 `/data/travel-notes/media-tmp`）。否则「init 在副本 A、chunk 落到副本 B」会 404（会话目录不在本机）。
4. **调度去重**：视频转码 sweep、DB 备份、清理任务只能由**一个**调度者执行（单副本跑，或外部 cron + 分布式锁）。crontab 在多机部署时要只装在一台。
5. **粘性对话（可选）**：分片上传/转码会话天然有副本亲和需求；按 §2-3 用共享卷后可以不做粘性。若暂不共享卷，可先按 `uploadId` 做一致性哈希粘性。
6. **日志聚合**：json-file 各自本地；多副本建议 Loki / ELK / 云日志（至少 `docker logs` 集中采集）。
7. **Nginx upstream**：多副本后 upstream 配多个 `server 127.0.0.1:300x`，开启 `max_fails/fail_timeout` + 被动健康检查。
8. **Next.js ISR / `.next/cache`**：每副本本地磁盘 → ISR 页面可能短时不一致。可接受则不管；要强一致需共享 cache 目录或把相关页改 `dynamic`。
9. **COSFS 一致性**：rename/unlink 最终一致。媒体变体先写本地临时目录、再整文件上传，避免其它副本读到半成品。
10. **数据库连接数**：副本数 × 连接池大小要小于 MySQL `max_connections`（当前每进程连接池见 `lib/prisma-adapter.ts`）。

## 3. compose scale 示例

当前 `docker-compose.yml` 的 `app` 固定了 `container_name` 与 `127.0.0.1:3000:3000` 端口映射，直接 `--scale` 会冲突。多副本请用 override 去掉这两项：

```yaml
# docker-compose.scale.yml（示例）
services:
  app:
    # 覆盖掉 container_name 与固定端口，交给 --scale 分配
    container_name: null
    ports: []
```

```bash
# 1) 起 Redis（可选但推荐）
docker compose --profile redis up -d

# 2) 起 3 个 app 副本（用 override 解开固定名/端口）
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --scale app=3 --build

# 3) 确认副本与共享状态
docker compose ps
docker compose exec redis redis-cli ping

# 4) Nginx upstream 示例（宿主机 nginx）
#   upstream tiantu { server 127.0.0.1:3000; server 127.0.0.1:3001; server 127.0.0.1:3002; }
#   proxy_pass http://tiantu;
```

注意：没有共享卷/Redis 时不要开多副本 —— 会立即出现 §1 标注 ⚠️ 的三类问题。

## 4. 验证命令（多副本上线前逐条跑）

```bash
# 健康检查：每个副本都应 200 且 status=ok（migrations/storage 也 green）
for p in 3000 3001 3002; do curl -s localhost:$p/api/health; echo; done

# Redis 连通与键空间（配置 REDIS_URL 后）
docker compose exec redis redis-cli ping                      # PONG
docker compose exec redis redis-cli --scan --pattern 'tn:cache:*' | head
docker compose exec redis redis-cli --scan --pattern 'tn:rl:*' | head

# 跨副本限流（相册解锁：IP 10 次/15min）：对 3000 连打 11 次，再打 3001
for i in $(seq 1 11); do curl -s -o /dev/null -w '%{http_code} ' -X POST localhost:3000/api/verify-album-password -H 'content-type: application/json' -d '{"date":"1999-01-01"}'; done; echo
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:3001/api/verify-album-password -H 'content-type: application/json' -d '{"date":"1999-01-01"}'   # 期望 429

# 跨副本缓存失效：副本 A 改旅行标题，立刻请求副本 B 详情应看到新标题（Redis tag 失效）

# 分片上传跨副本：init 在 3000，chunk 交替打 3000/3001/3002，complete 应成功（MEDIA_TMP_DIR 已共享）
```

## 6. 建议的迁移顺序

1. 先上 Redis（只让缓存共享；限流仍内存，行为不变，风险最低）→ 观察 `/api/health` 与日志无降级告警；
2. 分批把 34 处限流调用点改为 `rateLimitShared` / `*Shared`（每批跑单测 + 手工验证 429 语义）；
3. 设置 `MEDIA_TMP_DIR` 到共享卷，验证跨副本分片上传；
4. 单副本灰度通过后 `--scale app=2`，按 §4 验证；再扩到 3+；
5. 最后补调度去重、日志聚合、ISR 一致性（见 §2-4/6/8）。

## 7. 快速回滚

- 去掉 `REDIS_URL`（或注释掉）→ 全部回到进程内实现，**无需改代码**；
- `docker compose up -d --scale app=1` 回到单副本；
- Redis 服务可直接 `docker compose stop redis`（应用会在 500ms 内降级内存并打一条告警）。
