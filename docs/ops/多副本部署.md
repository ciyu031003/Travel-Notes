## 2. 仍需外部配置 / 决策

1. **Redis（可选，多副本强烈建议）**
   - `docker compose --profile redis up -d` 启动 `redis` 服务（只绑回环 `127.0.0.1:6379`，不持久化，`allkeys-lru` 128MB）；
   - 在 `.env` 设置 `REDIS_URL`：同一 compose 网络填 `redis://redis:6379`，app 跑在宿主机则 `redis://127.0.0.1:6379`；
   - 未配置 = 纯内存（与改造前**完全一致**）；配置但连不上 = 500ms 内降级内存并只打一条告警日志。
2. **限流调用点（已完成迁移，保留约定）**
   - 原 34 处同步 `rateLimit()` / `checkLoginLock()` / `recordLoginFailure()` / `clearLoginFailures()` 已全部改为：
     `await rateLimitShared(opts)`、`await checkLoginLockShared(key, opts)`、`await recordLoginFailureShared(...)`、`await clearLoginFailuresShared(...)`（`@/lib/infrastructure/rate-limit-factory`）；
   - key 维度（IP / user / 资源）、limit、窗口、429 body（`error` + `retryAfterSeconds`）与改造前完全一致；未配 `REDIS_URL` 时 `*Shared` 等价于原同步内存实现；
   - **新路由约定**：限流一律用 `*Shared`，不要再 import `lib/infrastructure/rate-limit` 的同步函数（那只保留给 `MemoryRateLimiter` 内部与单测）。
3. **媒体分片临时目录共享（部署配置）**：代码已全部走 `lib/media/tmp-dir.mediaTmpDir()`（图片分片 `tn-iuploads`、视频分片 `tn-vuploads`、转码 `tn-transcode-*`）。多副本部署时把 `MEDIA_TMP_DIR` 指向所有副本可见的卷（如 `/data/travel-notes/media-tmp`），否则「init 在副本 A、chunk 落到副本 B」会 404（会话目录不在本机）。
4. **调度去重**：视频转码 sweep、DB 备份、清理任务只能由**一个**调度者执行（单副本跑，或外部 cron + 分布式锁）。crontab 在多机部署时要只装在一台。
5. **粘性对话（可选）**：分片上传/转码会话天然有副本亲和需求；按 §2-3 用共享卷后可以不做粘性。若暂不共享卷，可先按 `uploadId` 做一致性哈希粘性。
6. **日志聚合**：json-file 各自本地；多副本建议 Loki / ELK / 云日志（至少 `docker logs` 集中采集）。
7. **Nginx upstream**：多副本后 upstream 配多个 `server 127.0.0.1:300x`，开启 `max_fails/fail_timeout` + 被动健康检查。
8. **Next.js ISR / `.next/cache`**：每副本本地磁盘 → ISR 页面可能短时不一致。可接受则不管；要强一致需共享 cache 目录或把相关页改 `dynamic`。
9. **COSFS 一致性**：rename/unlink 最终一致。媒体变体先写本地临时目录、再整文件上传，避免其它副本读到半成品。
10. **数据库连接数**：副本数 × 连接池大小要小于 MySQL `max_connections`（当前每进程连接池见 `lib/prisma-adapter.ts`）。

**剩余外部项（代码已就绪，只需部署/运维配置）**：

1. **Redis 服务与 `REDIS_URL`**（可选项；不配则单实例语义，多副本限额不共享）；
2. **`MEDIA_TMP_DIR` 指向共享卷**（NFS/COSFS/EFS 等；否则跨副本分片上传 404）；
3. **调度去重**：视频转码 sweep、DB 备份、清理 cron 只能单点执行；
4. **日志聚合**：Loki/ELK/云日志（compose 目前 json-file 本地轮转）；
5. **Nginx upstream + 健康检查**（多 server + `max_fails`）；
6. **DB 连接数核算**：副本数 × 连接池 < MySQL `max_connections`；
7. **ISR/`.next/cache` 一致性**：需要强一致时共享 cache 或相关页改 `dynamic`。

## 3. compose scale 示例

当前 `docker-compose.yml` 的 `app` 固定了 `container_name` 与 `127.0.0.1:3000:3000` 端口映射，直接 `--scale` 会冲突。多副本请用 override 去掉这两项：

```yaml
# docker-compose.scale.yml（示例）
services:
  app:
    # 覆盖掉 container_name 与固定端口，交给 --scale 分配
    container_name: null
    ports: []
```

```bash
# 1) 起 Redis（可选但推荐）
docker compose --profile redis up -d

# 2) 起 3 个 app 副本（用 override 解开固定名/端口）
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --scale app=3 --build

# 3) 确认副本与共享状态
docker compose ps
docker compose exec redis redis-cli ping

# 4) Nginx upstream 示例（宿主机 nginx）
#   upstream tiantu { server 127.0.0.1:3000; server 127.0.0.1:3001; server 127.0.0.1:3002; }
#   proxy_pass http://tiantu;
```

注意：没有共享卷/Redis 时不要开多副本 —— 会立即出现 §1 标注 ⚠️ 的三类问题。

## 6. 建议的迁移顺序

1. 起 Redis 并设置 `REDIS_URL` → 观察日志无 `[redis] 共享后端不可用…` 告警，`redis-cli --scan --pattern 'tn:*'` 有键；
2. 设置 `MEDIA_TMP_DIR` 到共享卷，验证跨副本分片上传（§4 最后一条）；
3. 单副本灰度通过后 `--scale app=2`，按 §4 逐条验证；再扩到 3+；
4. 最后补部署侧项：调度去重、日志聚合、ISR 一致性、DB 连接数（见 §2 剩余外部项）。

## 7. 快速回滚

- 去掉 `REDIS_URL`（或注释掉）→ 全部回到进程内实现，**无需改代码**；
- `docker compose up -d --scale app=1` 回到单副本；
- Redis 服务可直接 `docker compose stop redis`（应用会在 500ms 内降级内存并打一条告警）。

## 8. 运维细则（Nginx / DB 连接数 / ISR / 滚动发布 / 日志 / 调度）

### 8.1 Nginx upstream（两个 app 端口 + keepalive + X-Forwarded-*）

```nginx
upstream tiantu_app {
    # 两个副本分别监听 3000 / 3001（compose 用 --scale 时容器内部都是 3000，由 docker 端口映射或
    # 宿主机 nginx 直连 127.0.0.1:3000/3001；也可直接用 docker compose 的 service 名 + 自建 dns 解析）
    server 127.0.0.1:3000 max_fails=3 fail_timeout=15s;
    server 127.0.0.1:3001 max_fails=3 fail_timeout=15s;

    # 到上游复用连接，避免每请求三次握手（对 /api/health 这种高频探活尤其明显）
    keepalive 32;
    keepalive_timeout 60s;
    keepalive_requests 1000;
}

server {
    listen 443 ssl http2;
    server_name travel-notes.yuanabd.cn;

    location / {
        proxy_pass http://tiantu_app;
        proxy_http_version 1.1;          # keepalive 必须 1.1
        proxy_set_header Connection "";  # 清掉 close，才能复用 upstream 连接

        # 真实客户端信息（代码 getClientIp 优先 X-Real-IP；XFF 用 $remote_addr 覆盖，防伪造）
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;

        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 2;
    }

    # 健康检查（自建 /api/health，未就绪返回 503；upstream 的 max_fails 会据此摘副本）
    location = /healthz {
        access_log off;
        proxy_pass http://tiantu_app/api/health;
        proxy_connect_timeout 2s;
        proxy_read_timeout 5s;
    }
}
```

要点：

- `keepalive` 必须配 `proxy_http_version 1.1` + `proxy_set_header Connection ""`，否则连接池闲置；
- `X-Forwarded-For` **用 `$remote_addr` 覆盖**而不是透传 `$proxy_add_x_forwarded_for`：代码里 `getClientIp` 取 XFF 最后一段，透传会让客户端自带的首段参与伪造（P1-11 已按此实现）；
- 需要 App 壳跨域时，CORS 白名单由应用侧处理（`CORS_ALLOWED_ORIGINS`），Nginx 不要再加 `*`。

### 8.2 DB 连接数估算（pool 25 × 副本数 vs MySQL max_connections）

当前连接池默认值（`lib/prisma-adapter.ts` 的 `DB_CONFIG`，可用环境变量覆盖）：

| 参数 | 默认 | 环境变量 |
|---|---|---|
| 连接池上限 | 25 | `DB_CONNECTION_LIMIT` |
| 排队上限 | 50 | `DB_QUEUE_LIMIT` |
| 获取连接超时 | 10s | `DB_ACQUIRE_TIMEOUT` |

估算公式：**副本数 × `DB_CONNECTION_LIMIT` + 预留 ≤ MySQL `max_connections`**。

| 副本数 | pool 25 | 占用 | MySQL 默认 151 | 结论 |
|---|---|---|---|---|
| 1 | 25 | 25 | 151 | ✅ 余量充足 |
| 3 | 25 | 75 | 151 | ✅ 可用（预留 76 给备份/迁移/运维连接） |
| 5 | 25 | 125 | 151 | ⚠️ 接近上限：建议 `DB_CONNECTION_LIMIT=15`（75）或调大 `max_connections` |
| 8 | 25 | 200 | 151 | ❌ 必须调小 pool（如 12）或提高 `max_connections=500` |

建议：

- 多副本时把 `DB_CONNECTION_LIMIT` 跟着副本数**显式写进 `.env`**（不要依赖默认 25），并在扩容前用 `SHOW VARIABLES LIKE 'max_connections'` / `SHOW STATUS LIKE 'Threads_connected'` 核对；
- 另需为 `mysqldump` 备份、`prisma migrate`、人工排障各留 1–5 个连接；
- 连接被占满时应用会走 `DB_ACQUIRE_TIMEOUT`（10s）后报错，表现是「偶发 500/超时」，不是 DB 挂——扩容前先看 `Threads_connected`。

### 8.3 ISR / 静态页面缓存注意

- Next.js 的 `.next/cache` 在**每个副本本地磁盘**：滚动/多副本时同一页面在不同副本可能命中不同 ISR 产物，出现「刷新两次内容不一样」。
- 当前影响面：`/travel/[slug]`、`/space/[slug]` 等使用 `generateStaticParams` 的页面（构建期 + 增量再生成）；纯 `dynamic` 页面与 API 不受影响。
- 可接受则不管（内容最终一致，窗口 = revalidate 周期）；不可接受时三选一：
  1) 把相关页面标 `export const dynamic = 'force-dynamic'`（放弃 ISR，换一致）；
  2) 多副本共享 `.next/cache`（NFS 挂载，读写延迟会拖慢页面，需实测）；
  3) 页面内容改走已有的服务端缓存（Redis `CacheService`），让 HTML 本身保持动态。
- HTML 响应**不要**配长缓存/immutable：带用户态的页面必须 `private`，否则会串号（当前代码已按登录态区分）。

### 8.4 滚动发布与健康检查

发布顺序（零停机）：

1. 构建新镜像并 `docker compose up -d --scale app=3 --no-deps app`（新副本先起；旧副本仍在服务）；
2. 轮询每个新副本 `curl -fsS localhost:<port>/api/health` → 200 且 `status=ok`（`migrations`/`storage` 也 green）；
3. Nginx upstream 加入新副本端口，`reload` 生效；
4. 观察 5–10 分钟（5xx、`[redis] 共享后端不可用`、`[PrismaMariaDB]` 告警），再摘掉旧副本并 `docker compose stop`。

健康检查口径：

- compose 已内置 `healthcheck`（`/api/health`，interval 30s / timeout 5s / retries 5 / start_period 90s）；
- `/api/health` 返回 503 时**不要加流**：db 不通、迁移未完成、存储不可写都会 503；
- 回滚：`docker compose up -d --scale app=1` 回到单副本，或把镜像 tag 改回上一个（`server-rebuild.sh` 会记录 previous 镜像）。

### 8.5 日志聚合

- 现状：compose 用 `json-file` 轮转（`max-size: 20m`、`max-file: 5`），每容器本地文件。单机可 `docker compose logs -f --tail=200 app` 排查。
- 多副本建议二选一：
  1) **Loki + Grafana**：宿主 promtail（或 docker plugin）采集 `/var/lib/docker/containers/*/*-json.log`，按 `container_name` / `compose_service` 打标签；
  2) 云厂商日志服务（CLS / CloudWatch / Logtail），同样按容器采集。
- 应用日志已带结构化字段（如 `[redis]`/`[PrismaMariaDB]`/`[idempotency]` 前缀、`X-Request-Id` 透传），聚合后按 requestId 串联跨副本请求。
- 告警建议：`level=error` 速率、`[redis] 共享后端不可用` 出现即告警（说明共享状态降级）、5xx 比例。

### 8.6 调度去重结论（哪些必须单点）

扫描结论：**服务端没有常驻 cron / 业务定时器**。

| 位置 | 类型 | 多副本行为 | 是否需要单点 |
|---|---|---|---|
| `lib/prisma-adapter.ts`（`healthCheckTimer`） | 每副本 `setInterval` 60s 做 DB ping | 每副本各一份 | ❌ 不需要：只是 DB 连通性检查，成本 = 每副本每分钟 1 次 ping，非正确性问题 |
| `lib/infrastructure/video-transcode.ts`（`queue` + `sweepAndEnqueue`） | **进程内队列**，由上传请求触发 sweep | 每个副本各自入队；文件标记（`.transcoding`）在共享卷上可见，sweep 可补 | ❌ 正确性不依赖单点；极端情况下同一视频可能被两个副本各转码一次（产物幂等，成本可接受） |
| `lib/modules/offline/sync-engine.ts`（`retryTimer`） | 客户端（Capacitor App 内）定时器 | 只跑在用户设备上 | ❌ 与服务端副本无关 |
| `scripts/backup-db.sh` + `scripts/crontab.travel-notes` | 宿主机 crontab | 装到几台机器就会跑几份 | ✅ **必须单点**：只在一台装 cron（或在外部调度平台加分布式锁） |
| `docker-entrypoint.sh`（`migrate bootstrap` + `migrate deploy`） | 容器启动时执行 | 多副本同时启动会并发跑迁移 | ⚠️ 迁移是幂等的（`migrate deploy` 会跳过已应用），但建议发布时先起 1 个副本跑迁移、健康后再 `--scale` |
| 清理类脚本（`disk-clean.sh`、`gc-orphan-spaces.cjs` 等） | 手动/cron 触发 | 手动跑几次就执行几次 | ✅ 单点执行 |

结论：**唯一必须做「只跑一份」的是宿主机 cron（备份/清理）与迁移入口**；应用内的 healthCheckTimer 与转码队列是成本项，不影响正确性。

## 9. 自检脚本 `scripts/verify-multi-replica.cjs`

用途：上线/扩容前确认「Redis 可用」与「共享临时目录可写」，report-only、只读探测、自动清理。

```bash
node scripts/verify-multi-replica.cjs              # JSON 报告
node scripts/verify-multi-replica.cjs --self-test  # 判定逻辑自测（内存假对象，不连外部服务）
node scripts/verify-multi-replica.cjs --help
```

输出（stdout 单 JSON）：

| 场景 | 关键字段 | 退出码 |
|---|---|---|
| 未配置 `REDIS_URL` | `redis.status="not-configured"`，`mediaTmp.status="ok"`，`ok=true` | 0（单副本行为不变） |
| Redis 正常 | `redis.status="ok"` + `checks.{ping,cacheWrite,cacheRead,cacheTtl,rateLimitIncr,rateLimitExpire,cleanup}` 全 true | 0 |
| Redis 配了但连不上/探测失败 | `redis.status="fail"` + `redis.error`（URL 自动脱敏） | 1 |
| `MEDIA_TMP_DIR` 配了但目录不存在/不可写 | `mediaTmp.status="fail"` + `mediaTmp.error` | 1 |

探测内容（会自行清理）：

1. `SET tn:cache:probe:<rand> PX 2000` → `GET` 读回一致 → `PTTL` 在 (0, 2000]；
2. `INCR tn:rl:probe:<rand>` 期望 1 → `PEXPIRE 1000` → 再 `INCR` 期望 2 且 TTL 未被重置（验证限流窗口语义）；
3. 媒体目录写 `tn-health-probe-<rand>.tmp` → 读回一致 → 删除。

CI/发布脚本集成示例：

```bash
node scripts/verify-multi-replica.cjs > /tmp/mr.json || { cat /tmp/mr.json; exit 1; }
jq -e '.ok' /tmp/mr.json >/dev/null || { jq '.notes' /tmp/mr.json; exit 1; }
jq -r '.notes[]' /tmp/mr.json   # 人读提示（未配 Redis / 未配共享目录都会明确说明）
```

> 说明：`package.json` 的 script 别名由工程化线统一加（本批不改 package.json），命令以 `node scripts/...` 形式写入 CI/部署文档即可。
