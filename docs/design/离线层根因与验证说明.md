# 离线层根因与验证说明（1.16.6 – 1.16.10）

> 写给未来的自己 / 任何接手这个模块的人。
> 背景：连续多个版本的真机反馈都是「新建旅行进不去 / 没有编辑与添加行程按钮 /
> 没有自己建立的旅行记录」，反复修却始终不生效。这里记录**为什么**，
> 以及现在用**什么手段**防止同类问题再溜过去。

## 一、结论先说

这套离线层（本地 SQLite + 同步队列）**在 Android 上从来没有真正工作过**，
而且它出错时**完全静默**：不崩溃、不报错、界面上只是"没有数据"。

原因是当时所有测试都跑在 **Web 路径**上，而 Web 与 Android 在三个关键点行为不同：

| 维度 | Web（开发/测试） | Android（真机） |
|---|---|---|
| `db.query()` 返回的行 | 值数组 `[id, slug, …]` | **按列名索引的对象** `{id, slug, …}` |
| 连接生命周期 | 每次加载都是新的内存对象 | **原生侧连接跨 WebView 重载存活** |
| 表结构 | 每次全新建表 | **沿用老版本的表，`CREATE TABLE IF NOT EXISTS` 不补列** |

只要其中任何一条踩空，离线层就整体失效 —— 而它失效时看起来像"网络问题"或"没有数据"。

## 二、七个根因（全部已修）

| # | 根因 | 后果 | 修复 |
|---|---|---|---|
| 1 | `toRows()` 只认数组行（`Array.isArray` 过滤），Android 的对象行被整行丢弃 | **所有本地读返回空**；同步队列 `list()` 也恒为空 → SyncEngine 认为无待上传项 → **用户创作从未上传到云端**（线上库 `Travel=0`） | 1.16.6 归一化两种行结构 + `rowGet()` 按列名取值 |
| 2 | `getOfflineDb()` 直接 `createConnection`；原生侧连接仍在时抛 `already exists`（`CapacitorSQLite.java`） | WebView 重载后**整个离线层失效** | 1.16.7 `checkConnectionsConsistency` → `isConnection` → 复用 `retrieveConnection` |
| 3 | `CREATE INDEX idx_sync_queue_status ON sync_queue(status,…)` 排在列自愈**之前**且不容错 | 老设备缺列时初始化直接失败 | 1.16.8 顺序改为 建表 → 列升级 → 自愈 → 逐条容错建索引 |
| 4 | `DESIRED_COLUMNS` 漏了 `sync_queue` / `social_post` / `album_media` / `memory_media` / `meta` | 这些表永远不会被自愈；`sync_queue` 缺列 → 队列读写整条抛错 → 无法上传 | 1.16.8 补全 + 结构一致性守卫测试 |
| 5 | `applyPullEntity` 用服务端返回的**全部字段**拼 SQL | 服务端新增字段 → 旧版 App 本地表没那列 → 整批拉取失败，离线缓存再也不更新 | 1.16.9 按 `tableColumns()` 过滤 |
| 6 | `pullEntityTypes` 无任何 try/catch | 一条脏数据/一个类型失败 → **整轮拉取全灭**，外层 `void sync()` 吞掉 | 1.16.9 逐类型 + 逐条隔离 |
| 7 | 离线层失败无痕迹 | 无法区分"离线层坏了"与"离线层正常但没数据"，导致前几版修错方向 | 1.16.10 `getOfflineInitError()` + 诊断信息 + 同步页展示 |

此外（更早，同一批真机反馈的另一半）：
- 同步分发器只认 `{data:{id}}`，而写接口返回 `{success,id,slug}` → `remoteId` 永远回填不上 →
  `pendingSync` 恒为 true → **编辑/添加行程/删除按钮永远不出现**（1.16.2 修）
- 创建后不触发展示上传（1.16.2 改为在线优先直写）
- 写入路径（行程天 / 回忆 / 相册 / 碎碎念）在原生端**只写本地**（1.16.3 / 1.16.4 统一为 `writeThrough`）
- 空间内旅行「成员读不到、只读成员却能看到」的读写口径不一致（1.16.2 修）
- 「仅自己」实际落库为 `SPACE`（空间成员可见）—— 真实泄露（1.16.2 修）

## 三、现在的验证手段（关键）

**真机行为无法在 CI 里复现，但可以用"真引擎 + 真语义"逼近。**
以下测试全部是"先能测出旧缺陷（变异验证），再证明修好了"：

| 测试文件 | 覆盖 |
|---|---|
| `tests/unit/offline-sqlite-rows.test.ts` | 两种行结构归一化、键序打乱、null/0/空串、聚合别名 |
| `tests/unit/offline-android-contract.test.ts` | 假库返回**列名对象且键序打乱**，跑真实调用链（队列 / 旅行读 / remoteId 查找） |
| `tests/unit/offline-real-sqlite.test.ts` | **Node 24 内置 `node:sqlite`**（真 SQLite，`all()` 返回列名对象 = Android 语义）：真实初始化、写入→读取→队列闭环、老设备缺列自愈、拉取 LWW/墓碑/健壮性 |
| `tests/unit/offline-schema-consistency.test.ts` | 从 `CREATE_TABLES_SQL` **解析**真实列，要求自愈清单逐表逐列覆盖（双向） |
| `tests/unit/offline-db-connection.test.ts` | 连接复用（重载不抛 already exists）、初始化失败留下可诊断原因 |
| `tests/unit/offline-sync-engine.test.ts` | 阶段隔离（本地队列读失败仍须上传）、上传后回写失败不得重传 |
| `tests/unit/offline-write-through*.test.ts` | 在线优先/本地兜底的契约、在线成功后必须清队列（防重复数据） |
| `tests/e2e/travel-native-shell.spec.ts` | 注入 `isNativePlatform()=true` 且无 SQLite 插件（= 真机"本地存储不可用"），走完整 UI 链路 |

**改这个模块时的硬性要求**：
1. 不要用 `row[0]` / 位置解构读查询结果 —— 一律 `rowGet(row, '列名')`。
   键序在 Android 上没有保证（org.json 实现细节）。
2. 新增列必须同时加进 `DESIRED_COLUMNS`，否则老设备永远补不上（有守卫测试，会红）。
3. 写本地/拉取落地都要"按真实列过滤"，不要假设表结构是最新的。
4. 任何"批量循环"都要逐条隔离，不要让它整轮中断。
5. 失败要留痕（`lastError` / `getOfflineInitError()`），不要静默。

## 四、真机验证清单（需要手机，我无法代做）

按顺序做，每步失败都请在失败页点「复制诊断信息」：

1. **联网**新建旅行（可顺手选一个空间）→ 是否直接进入详情页
2. 详情页是否有「编辑信息」按钮；⋯ 菜单里是否有删除/公开
3. 「行程」页签：添加行程 → 是否立刻出现；返回再进入是否还在
4. 「记一笔」：写文字 + 选照片 → 是否立刻出现、照片是否显示
5. 「花销」页签：记一笔费用
6. 「我的 → 数据与同步」：是否显示「离线存储不可用」
7. **杀进程重进**：上面内容是否都还在
8. **开飞行模式**再打开：离线内容是否可看、能否离线记录
9. 恢复网络后：离线记录是否自动上传（「数据与同步」里待上传数是否归零）
10. 空间：把一本旅行放进空间 → 用另一个账号（成员/只读）看是否分别可编辑/只读
