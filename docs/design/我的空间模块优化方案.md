## 0. 结论前置（先看这 7 条）

1. **后端建了 80%，前端只用了 20%。** `Space / SpaceMember / SpaceInvite`、RBAC、邀请码、空间可见性读路径（`canViewResource`）都在；但前端只有一个 `SpacePanel` 弹窗，**没有空间详情页、没有空间切换、没有空间配色**。

2. **最要命的问题不是 UI，是一列数据。** `SpaceMember.userId` 在任何「加入空间」的路径里**从来不写**（`space.repository.ts:200-206`）。而权限判定有**两套键**：`lib/modules/space/permissions.ts` 用 `username`，`lib/modules/access`、`album.service.canManageAlbum`、`travel.service.myActiveSpaceIds`、`getUserCapabilities` 全用 `userId`。后果有两个，方向相反：
   - **协作彻底不通**：用邀请码加入的成员，`userId` 为 NULL → 一切按 `userId` 判定的能力全部返回 false → **他看不到、也改不了空间里的任何旅行/相册/回忆**（`travel/api-guard.ts:52`、`access/index.ts:45-52`）。你这次要的「空间内用户可以一起修改旅行、相册」，现在被这一列挡住了。
   - **越权**：`getUserCapabilities` 用 `memberships.length === 0` 反推「无空间 = 单用户 = OWNER」（`permissions.ts:127`）。成员在 `userId` 键下查不到成员身份 → **被判定成 OWNER**，拿到 `canManageSettings / canManageSocial / canViewAudit`。

3. **相册读路径漏了空间范围。** `listAlbums` / `getAlbum` 用的是 `scopedWhere(userId)`（`album.service.ts:98-114`），**只认 `userId` 和 `isPublic`，不含 `spaceId ∈ 我的空间`**。而 `canManageAlbum` 又支持空间 OWNER/MEMBER（`album.service.ts:348-364`）→ **能改、但列表里看不到**。这和第三轮已经修掉的 `listTravels` 是**同型 bug**（`travel.service.ts:113-129` 已修，相册漏修）。

4. **两套空间 UI 并存且互不相同。** `components/space/SpacePanel.tsx`（移动端弹窗：有类型选择、**没有邀请记录/角色/过期状态**）vs `app/admin/spaces/page.tsx`（桌面后台：成员头像堆叠 + 邀请记录 + 角色 + 撤销，**没有类型选择** → 在后台建的空间类型永远是 `OTHER`；且用了项目规范明令禁止的渐变与冷色 `from-pink-500 via-indigo-500 to-purple-400`）。收敛成一套，是本次的骨架工作。

5. **还有一个「建不出空间」的硬 bug。** `SpaceService` 的 `SLUG_RE = /^[a-z0-9-]{2,80}$/`（`space.service.ts:10,47`）只允许 ASCII，而 `SpacePanel` 用**保留中文**的规则生成 slug（`SpacePanel.tsx:235`，占位文案还写着「我们的小家」）→ **任何中文名空间创建都会 400**。真库佐证：34 个空间全是自动创建的 `personal-*`，**没有一个用户自建空间**。

6. **配色需要先给设计规范开一个口子。** 现在 `spaceType` 对 UI 的唯一影响是一个 emoji（`SpacePanel.tsx:52-58`，而且用 emoji 冒充图标，违反规范 §1 第 7 条）。要「每类空间一套清新淡雅配色」，就得先改《移动端设计规范》§2.6「禁止用彩色表达分类」与单一强调色纪律——我建议**受控多主题**：只放行 7 个低彩度令牌，中性层/品牌赤陶/间距/圆角/字号全部共享，并用 `[data-space]` 作用域把影响面锁在空间模块内。详见 §3。

7. **建议的节奏**：P0 纯后端修 4 个地基问题（1–2 天，收益最大、风险最低）→ P1 空间模块 UI + 主题 → P2 协作内容（共享范围 / 归属 / 活动流）→ P3 打磨（纪念日与碎碎念共享等）。

## 2. 目标、原则与不做的事

### 2.1 目标

1. **能一起改**：空间成员（OWNER/MEMBER）可以共同创建与编辑该空间下的旅行、行程、回忆、照片与相册；VIEWER 只读。
2. **能一起看**：空间详情页把「一起记录的旅行 / 一起经营的相册 / 共同的回忆 / 正在规划」聚合到一个可分享的空间主页。
3. **每类空间有自己的颜色**：情侣=薄荷、家庭=鸢尾、朋友=天青、独旅=梅、其他=沙；全部低彩度、清新淡雅，明暗双主题，AA 达标。
4. **看得见协作**：成员头像堆叠、角色徽标、内容归属（谁建的 / 最近谁改的）、空间活动流。
5. **维持工程纪律**：不新增运行时依赖；颜色全走 token；组件零裸 hex；`node scripts/check-design-tokens.mjs` 不退化。

### 2.2 原则（沿用项目既有约定）

- **不推倒重写**：在现有 `Space / SpaceMember / SpaceInvite` 上做增量，P0–P2 **不改 schema**（P3 的纪念日/碎碎念共享才需要加列）。
- **权限只有一套实现**：所有新代码走 `lib/modules/access`，禁止各 API 各写一份（历史上 IDOR 都出在「抄漏一处」）。
- **颜色只有一处声明**：`app/globals.css` 声明 token，组件只写 `bg-[var(--space-accent)]`。
- **抄代码只抄 MIT / Apache-2.0 / BSD**（沿用《移动端三轮优化方案》§10.4 的许可证硬规则）。
- **移动端优先**，桌面零回归（差异走 `md:` 断点）。

### 2.3 明确不做（本轮）

| 不做 | 原因 |
|---|---|
| 实时协同（多人在线光标 / 行程实时同步 / CRDT） | 需要实时通道 + 冲突合并，成本远超收益；「乐观并发 + 冲突提示」覆盖 95% 场景 |
| 空间内群聊 / 投票 / 接龙 | 已有「评论式建议」路径（第四轮方案），不另起一套 |
| 空间级自定义配色（用户自选色） | 先用五套受控主题验证；自由配色必然破坏 AA 与品牌一致性 |
| 成员级权限细分（按资源授权） | `OWNER/MEMBER/VIEWER` 三档已够；不加 `SpacePermission` 表 |
| 团队/班级等更多空间类型 | 无真实需求前不加（`SpaceType` 可扩展） |

## 3. 配色方案：五类空间，五套清新淡雅

> 完整色值、逐项对比度计算与许可证核验见 [空间类型配色系统-研究报告.md](空间类型配色系统-研究报告.md)。本节只放结论与落地方式。

### 3.1 为什么要先改一条规范

《移动端设计规范》§2.6 明确写着「❌ 用彩色表达『分类』（分类用暖色 tone，不用冷色）」，§2.2 规定 `--m-accent` 是**唯一强调色**，§1 还要求彩色面积 ≤15%。「每类空间一套配色」与这些条款直接冲突。

**建议做法（而不是偷偷破例）**：给规范增加一节「§2.8 受控多主题（仅空间模块）」，同时把 `scripts/check-design-tokens.mjs` 的规则补成机制：

- 新增 token 名必须能在 `app/globals.css` / `app/mobile.css` 命中（checker 第 8 条已能自动校验，等于免费获得保护）；
- 新增一条检查：`components/space/` 与 `components/album/space/` 之外**不得**出现 `--space-*` 变量；
- 明确「`--space-*` 只能出现在 §3.2 列出的 7 个令牌上」。

### 3.2 允许随空间变化的令牌（仅 7 个）

| 令牌 | 用途 | 亮色取 Radix | 暗色取 Radix |
|---|---|---|---|
| `--space-accent` | 强调色（装饰/大色块，**禁止承载小字**） | step 9 | step 9 |
| `--space-accent-strong` | **主 CTA 填充、激活态、关键数字** | step 11 | step 11 |
| `--space-accent-soft` | 淡染底（标签/徽章底） | step 3 | step 4 |
| `--space-accent-text` | 淡染底/渐变上的文字 | step 12 | step 12 |
| `--space-on-accent` | CTA 填充上的文字 | `#FFFFFF` | `#080808` |
| `--space-hairline` | 装饰性发丝线/描边 | step 6 | step 6 |
| `--space-hero-a` / `--space-hero-b` | 空间头图渐变两端（**不承载小字**） | step 2 → 4 | step 5 → 3 |

**必须全局共享、禁止按空间覆写**：`--social-bg #F7F4EE`、`--social-surface #FFFFFF`、`--social-text #2B211B`、`--social-line`、阴影/圆角/间距/字号阶梯、以及品牌赤陶 `#A85F3A / #8A4A2B`（Logo、全局导航、设置页 CTA 始终是品牌色）。暗色共享 `#080808 / #111111 / #E8B36A`。

> 「中性层完全共享 + 只换 7 个低彩度变量」是「5 个主题不像 5 个 App」的全部秘密。模式借鉴 [daisyUI 的主题变量模型](https://github.com/saadeghi/daisyui/discussions/1811)（MIT）：一套语义变量 + 一个作用域选择器。

### 3.3 五套主题色值（亮 / 暗）

色源均为 [Radix Colors](https://github.com/radix-ui/colors)（**MIT**，已核验 LICENSE）。

| 空间 | 色相（Radix） | 亮：CTA 填充 `--space-accent-strong` | 白字对比 | 暗：CTA 填充 | `#080808` 字对比 |

| **FRIENDS 朋友空间** | sky 天青 | `#00749E` (sky 11) | **5.26 ✅** | `#75C7F0` (sky 11) | **10.67 ✅** |

### 3.4 色相分配理由（含中文语境的约束）

| 空间 | 色相 | 理由 |
|---|---|---|
| 情侣 | **薄荷绿** | 绿色在中文里承载「长青 / 和睦 / 生机」，且**天然避开两处文化雷区**：正红（已被品牌赤陶占用，低彩度红会显脏）、纯白（丧仪）。低彩度绿也是「情侣」品类里最不显幼稚的选择。**必须偏青/薄荷，绝不能偏黄**（黄绿=橄榄，中文语境有负面联想） |
| 家庭 | **鸢尾紫** | 「紫气东来」——紫在东亚的正面度显著高于西方（西方紫偶有丧色联想）。选 iris 而非 plum：蓝相更沉稳，贴合家庭相册「可信/归档」的气质 |
| 朋友 | **天青蓝** | 蓝=信任、开阔、旅途天空，社交场景最安全的色相；也是唯一能在「活泼」与「淡雅」之间不越界的冷色。避免黄/橙（与品牌赤陶同区，会稀释品牌） |
| 独旅 | **梅紫** | 独旅语义是「向内、黄昏、自我对话」；plum 是五个色相里最「低语」的一支，与 iris 相距 27° 且明度差明显，不会串味 |
| 其他 | **沙色** | fallback 的正确姿态是「安静、不主张」。sand 与暖纸底 `#F7F4EE` 同族、彩度≈0，绝不与其他主题争抢 |

由强调色色值反推色相：品牌赤陶 ≈20°，薄荷 ≈170°、天青 ≈196°、鸢尾 ≈242°、梅 ≈292°，沙为低彩度中性。**相邻主题最小间隔 ≈26°（薄荷↔天青）**，但二者明度与彩度差异明显、实机可辨；**离品牌色最近的是梅（≈88°）**，五套主题都不会与品牌赤陶混淆。

### 3.5 三个必须知道的硬结论（会影响实现）

1. **Radix 9 级不能当亮色 CTA**：mint 9 `#86EAD4` 对白字仅 **1.43**，sky 9 `#7CE2FE` 仅 **1.48**，远不达 4.5。→ 亮色 CTA **一律用 11 级**，9 级只做装饰/大色块。
2. **teal 11 `#008573` 在暖底 `#F7F4EE` 上只有 4.16，不达 AA** → 家庭弃 teal，改用 iris。
3. **Radix 6 级发丝线只有 1.4–1.6:1，不满足 WCAG 1.4.11 的 3:1** → 规定：**控件边界**（输入框/按钮/tab）必须用共享 `--social-line`；空间色 6 级**只作纯装饰分隔线**；**聚焦环不随空间变色**。

另：暗色下 11 级是**浅色实心**，白字反而只有 4.2–4.7 → `--space-on-accent` 必须切换成 `#080808`。

### 3.6 落地形态（组件零硬编码）

```tsx

export function SpaceThemeScope({ type, children }: { type: SpaceTypeValue; children: React.ReactNode }) {
  return <div data-space={type}>{children}</div>
}
```

```ts
// lib/mobile/space-system.ts —— 镜像 lib/mobile/icon-system.ts 的既有模式
export const SPACE_TYPE_LABELS: Record<string, string> = {
  COUPLE: '情侣空间', FAMILY: '家庭空间', FRIENDS: '朋友空间', SOLO: '独旅空间', OTHER: '空间',
}
export const SPACE_TYPE_ICON  = { COUPLE: HeartHandshake, FAMILY: UsersRound, FRIENDS: Users, SOLO: MountainSnow, OTHER: Sparkles }
export const SPACE_TYPE_TONE  = { COUPLE: 'blush', FAMILY: 'sun', FRIENDS: 'accent', SOLO: 'neutral', OTHER: 'neutral' }  // 徽标仍走暖色 tone
```

组件内只写 `bg-[var(--space-accent-strong)] text-[var(--space-on-accent)]`，**禁止裸 hex**。

### 3.7 ≤15% 彩色面积 · 每次上线自检（7 条）

1. 单屏内所有 `--space-accent*` 像素和 ≤ 屏面积 15%（含 CTA、激活态、徽标）；
2. 彩色只出现在：主 CTA / 激活态 / 关键数字 / 内容图片；**不得**用于页面底、卡片底、列表分隔、正文颜色；
3. 每屏最多 1 个 `--space-accent-strong` 实心 CTA；
4. `--space-accent-soft` 仅小面积标签底，单块 ≤ 屏 4%；
5. 头图渐变仅限头图区且高度 ≤ 屏 35%，渐变内文字一律 `--space-accent-text`；
6. 品牌赤陶仍出现在全局层（Logo / 导航 / 设置），切空间不丢品牌；
7. 暗色下 soft 面积上限降到 8%（暗底上色块视觉权重更大）。

## 5. 信息架构与页面设计

### 5.1 入口与导航

```
「我的」页 /me
  └─ 我的空间（区块，显示我加入的空间数量 + 类型色点）
       └─ /space           空间列表 · 切换器 · 创建 / 加入
            └─ /space/[slug]  空间详情（协作主场）
```

- `MeHome.tsx:414-436` 现在的入口按钮文案是「情侣 / 家人 / 朋友空间」且点击弹 `SpacePanel`。改为**直接跳 `/space`**，并显示「我有 3 个空间 · 💚情侣 🟣家庭 🔵朋友」这样的实况摘要（不再是一个静态弹窗）。

### 6.2 谁能改什么（RBAC × 资源）

| 操作 | OWNER | MEMBER | VIEWER | 非成员 |
|---|---|---|---|---|
| 查看空间内容 | ✅ | ✅ | ✅ | ❌（明确拒答，不泄露） |
| 新建/编辑旅行、行程、期望清单、花费 | ✅ | ✅ | ❌ | ❌ |
| 写回忆 / 传照片 / 整理相册 | ✅ | ✅ | ❌（见 §9-7） | ❌ |
| 参与「下一趟计划」的讨论与建议 | ✅ | ✅ | ✅（只读+可评论？见 §9-7） | 视 `visibility` 而定 |
| 邀请成员 / 生成邀请码 | ✅ | ❌ | ❌ | ❌ |
| 调整角色 / 移除成员 | ✅ | ❌ | ❌ | ❌ |
| 改名 / 改类型 / 换封面 / 解散空间 | ✅ | ❌ | ❌ | ❌ |
| 转让主人 | ✅ | ❌ | ❌ | ❌ |

服务端实现：写操作一律 `canActOnContent`（`lib/modules/access`）+ `requireCapability`；空间管理操作走 `requireSpaceOwner`（**修完 §7-A 后两种键就一致了**）。

### 6.3 归属与「谁改的」（P2，零改库）

| 展示 | 数据来源 | 说明 |
|---|---|---|
| 内容的创建者 | `Travel.ownerId` / `Album.userId` / `Memory.createdBy` | 已有字段，配合 `User.nickname/avatarUrl` 显示 |
| 最近修改时间 | `Travel.updatedAt` / `Album.updatedAt` | 已有字段 |
| 最近修改者 | **无字段** | 两种方案：① P2 只显示「最近修改 3 小时前」，不显示人；② 从 `AuditLog` 里 `resourceType + resourceId` 反查最近一次 `UPDATE` 的 `username`（零改库，但要求内容写操作补写审计日志）。**推荐 ②** |
| 空间动态流 | `AuditLog where spaceId` + `[spaceId, createdAt]` 索引 | 已存在，只需在内容写路径补写 `AuditLog`（`CREATE/UPDATE/DELETE/UPLOAD_MEDIA`，`spaceId` 非空时才写） |

> 这一块是本方案里性价比最高的一环：**不加一张表、不加一列，就能让「一起经营」有可见的痕迹**。

### 6.4 并发与冲突（P2，零改库）

不做实时同步，做**乐观并发**：

1. 客户端提交更新时带上读到的 `updatedAt`；
2. 服务端比对：不一致 → 返回 `409` + 「这条记录刚被 <用户名> 改过，请刷新后重试」；
3. 前端把冲突提示做成 `Toast`（语义色），**不静默覆盖**；
4. 同一用户连续编辑（自己改自己）不触发冲突。

### 6.5 通知（P2）

复用现有 `Notification`（`NotificationType` 已有 `COMMENT/LIKE/FOLLOW/FAVORITE/SYSTEM`，**不新增枚举**）：

- 有人加入空间 → 通知全体 OWNER；
- 空间内新增旅行/相册/回忆 → 通知**其他**成员（不通知操作者本人）；
- 有人被移除/角色变更 → 通知本人；
- 计划被评论/建议 → 通知发起人（第四轮方案已覆盖）。

### 6.6 可见性三档在空间里的语义（保持不变，补一个控件）

| 值 | 含义 | 谁可见 |
|---|---|---|
| `PRIVATE` | 仅自己 | 仅创建者（**即使同空间成员也看不到**） |
| `SPACE` | 空间成员可见（**默认**） | 该空间 ACTIVE 成员 |
| `PUBLIC` | 公开到旅行圈 | 所有登录用户 |

⚠️ 第三轮方案 §4.3 已指出：**旅行详情页现在没有任何可见性控件**（`TravelInfoEditor` 只有标题/地点/日期/描述），用户根本设不了。本次顺带补上——它是「空间里也有私密内容」这条产品语义的前提。

## 7. 关键修复（P0）：地基先修，UI 才有意义

### A. 成员身份链（最高优先级）

**改动**：`lib/modules/space/space.repository.ts`

```ts
async addMember(spaceId: number, username: string, role: SpaceRole): Promise<void> {
  // 新增：解析并写入 userId。
  // 为什么必须做：permissions.ts 按 username 判定，而 access/album/travel/capabilities
  // 全部按 userId 判定。不写 userId ⇒ 邀请加入的成员在「userId 世界」里不存在：

}
```

1. `lib/modules/space/permissions.ts#getUserCapabilities` 不能再靠 `memberships.length === 0` 判断。改为**同时按两种键查**成员身份：

   ```ts
   const memberships = await prisma.spaceMember.findMany({

     select: { role: true },
   ```

### B. 相册读路径补空间范围

**改动**：`lib/modules/album/album.service.ts#listAlbums / getAlbum`

镜像 `listTravels` 的 R3 修法：

```ts
const spaceIds = await myActiveSpaceIds(userId)
const where = userId
  ? spaceIds.length
    ? { OR: [{ userId }, { isPublic: true }, { spaceId: { in: spaceIds }, visibility: { in: ['SPACE', 'PUBLIC'] } }] }
```

**改动**：`lib/modules/space/space.service.ts` + `SpacePanel`/`/admin/spaces`

- 之所以不让 slug 支持中文：`/space/[slug]` 要进 URL 与分享链接，ASCII 更稳（编码、大小写、复制粘贴都少一类问题）。

- 仅 OWNER（`requireSpaceOwner`）；
- 名称 2–200 字；类型必须在 `SpaceType` 白名单内；封面走 sharp 变体链（复用 `app/api/me/cover` 模式）；

### E. 孤儿空间治理（数据卫生）

真库 30/34 是 `ensurePersonalSpace` 建的孤儿空间（用户已删、成员行已无）。`deleteSpace` 要求成员身份 → 这些空间**永远清不掉**，且会在 `Media`/`Memory` 上留引用。

3. 给 `SpaceMember.userId` 补外键约束（对齐 schema 声明），或显式在 schema 里注明「本库不加外键」，消除漂移。

## 10. 不破坏的边界

- **P0–P2 不改 `prisma/schema.prisma`**（P3 的 `Moment`/`Anniversary` 共享才需要，且届时先停来说明）。
- **不绕过权限层**：新接口一律 `requireAuth` → `canViewResource/canActOnContent` → `requireCapability/requireSpaceOwner`，禁止在路由里手写 `where`。
- **不新增运行时依赖**（唯二例外：Modal 焦点陷阱的 Radix Dialog 或手写 40 行，需附 bundle 对比）。
- **不动**：旅行圈可见性/路由、`GalaxyAlbumScene` 等相册沉浸模式、`/api/admin/*` 的既有契约、`ensurePersonalSpace` 的对外行为。
- **不改** `scripts/docker-entrypoint.sh` 的启动路径（既有隐患另立任务，见第三轮方案 §「R1 上线发现的一个既有隐患」）。
- 每期结束跑：`npm run typecheck` + `npx vitest run` + 相关 Playwright E2E + `node scripts/check-design-tokens.mjs`，并回归首页 / travel / album / circle / me / admin、深浅色两套主题。
- 抄进来的文件**顶部注明来源（仓库 + 文件 + 许可证）**（沿用项目既有约定）。
