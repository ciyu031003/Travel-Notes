## 0. 先说一件必须澄清的事：第 2 条我复现不出来

你说「旅行圈点开我公开的旅行会跳回首页」。我在**生产环境**用真实浏览器 + 真实账号跑了 4 组对照（脚本已留在仓库）：

| 场景 | 脚本 | 结果 |
|---|---|---|
| B 看 A 的公开旅行，坐标点击卡片 | `scripts/diag-circle-click.cjs` | ✅ 进 `/circle/69`，标题 612ms 出现 |
| 旅客圈点击（客户端路由）vs 直接进 URL | `scripts/diag-circle-clientnav.cjs` | ✅ 各 204ms / 236ms 都正常，**无 JS 报错** |
| 作者点自己的卡片 | `scripts/diag-circle-roles.cjs` | ✅ 进 `/circle/70` |
| 详情接口耗时 | `scripts/diag-circle-detail-timing.cjs` | ✅ 51ms |

**结论：`/circle` → `/circle/<id>` 这条链路在当前线上版本是通的，跳首页我复现不出来。**

我确实抓到两个**真实**的相邻缺陷，很可能就是你实际遇到的现象来源：

1. **游客点不进旅行圈**：`/circle` 未在公开路径白名单里 → 未登录点「旅行圈」直接 307 到 `/login?redirect=%2Fcircle`。你如果当时是未登录/掉登录状态，就会看到「点一下，人被弹走」。而 `/circle/<id>` 同样要登录。
2. **详情页首帧是「加载中…」**：`PostDetail` 在 `loading` 期间渲染的是整页居中的 spinner（`app/circle/[postId]/CirclePostShell.tsx` → `components/social/PostDetail.tsx:199`）。在真机弱网下这一帧会停留可见，体感就是「点了没反应 / 跳到别处了」。

所以我**不打算按「有一个 redirect bug」去改**，而是按「把这条路由做成不可能出错」去改（见 §3）。如果你手上有稳定的复现步骤（哪个账号、从哪个页面、点哪一张卡），发我，我按你的路径再验一遍——但方案不等它。

## 2. 第一轮：「我的」页重构

### 2.1 先修一个数据正确性 bug（这是我审计时发现的，比样式重要）

`/api/me` 的统计口径来自**旧的文章模型**，不是 App 里真实在用的旅行模型：

```ts
// lib/modules/social/profile.service.ts:111
const travels = await prisma.post.findMany({
  where: { userId, type: 'travel', published: true },   // ← Post，不是 Travel
```

而 App 里「+ 新建旅行」写的是 `Travel` 表。**结果：你在 App 里建的旅行，全都不计入「多少次旅行 / 多少地方 / 多少张照片」**，那三个数会偏低甚至为 0（只有历史上从后台发的旧文章才算）。这也解释了为什么「最近的一次旅行」有时是空的。

修：`getMyProfile` 改为以 `Travel` 为准（`ownerId = userId`，或所在 ACTIVE 空间的旅行），口径与 `/travel` 列表完全一致：

- `travelCount` = 去重后的 Travel 数
- `placeCount` = `Travel.location` 去重数（保留 `provinceCount` 作为补充字段，可选用「N 省 M 城」表达）
- `photoCount` = `Travel.coverMedia` + 该旅行所有 `Memory.media` + `MemoryMedia` 去重后的张数
- 顺带新增 `upcomingTravel`（`status = PLANNED` 且 `startDate >= 今天` 的下一趟），给「我的」页与空间页复用

> 这条修完，你截图里那三个数字才有意义。建议排在第一。

### 2.3 Hero 头部设计（回答「一半背景放风景图」）

结构（从上到下，都在同一个 `m-card` 里）：

```
┌───────────────────────────────────────┐
│  风景头图（用户上传，比例 16:9）        │  高 ≈ 44vw，object-cover
│  右上角：编辑资料 · 换头图（小图标）    │  图上只放这两个动作
│  ← 底部渐隐遮罩，让下行卡片自然压上来   │
├───────────────────────────────────────┤
│  ◯头像 92        「昵称」  [ID 徽章]    │  头像 -28px 上浮压住头图
│  （右下角相机角标） 签名一行            │
├───────────────────────────────────────┤
│   12 次旅行 │ 8 个地方 │ 236 张照片     │  不透明卡，不被头图干扰
├───────────────────────────────────────┤
│  [ 记录一次旅行 ]  [ 打开旅行画册 ]      │
└───────────────────────────────────────┘
```

关键点：
- **统计必须在头图之外**、位于不透明层上——这是你「统计在风景图上方/不被压住」的要求；用「图在上、卡在下」而不是「图上盖字」，护眼且可读性稳。
- 头像用 `-mt-7` 上浮，压住头图下缘 1/3，是全页唯一的层叠关系。
- 头图未上传时用当前 `--m-surface-2` 渐变 + 一处 `Images` 占位图标，不出现空白破版。
- 图上不放统计、不放名字（名字在卡内），避免「图上白字 + 复杂背景」的可读性灾难。

## 3. 第二轮：旅行圈路由加固 + 帖子详情升级

### 3.1 路由加固（不假设某个 redirect 存在，而是让它不可能出错）

1. **`/circle` 与 `/circle/<id>` 对游客开放（只读）**：在 `lib/public-paths.ts` 的 `PUBLIC_READ_PATHS` 增加 `'/circle'`、`'/circle/'`（只放 GET），写操作照旧要登录。这样「公开旅行」真的对未登录者可看，也消灭「点一下被踢去登录」这个最像你描述的现象。`/circle/user/<id>` 保持需登录。
2. **统一入口 `openPublicTravel({ slug, postId })`**：所有卡片/通知/后台入口都调它，内部只在「有 postId 才去 `/circle/<id>`，否则退到 `/travel/<slug>`」，杜绝 `'/circle/' + undefined` 这类 URL。
3. **详情页首帧不再是「加载中…」整页 spinner**：`PostDetail` 的 loading 换成骨架屏（沿用 `components/mobile/Skeleton`），并且**封面 + 标题先渲染**（接口把 `title/summary/cover` 放进首屏可见的乐观态），弱网下也有内容。
4. **静默失败兜底**：详情请求失败时不再只留白屏，渲染「这篇还在路上」+「返回旅行圈 / 直接看完整旅行」两个动作，并且**保留 URL**（不 redirect）。
5. **加一条 E2E 挡住回归**：`tests/e2e/circle-open.spec.ts` —— 游客 + 登录用户各自从 `/circle` 点卡片进详情，断言 URL 与标题；再断言 `/circle/<id>` 直开 200。这样「跳首页」若真存在任何变体，会被测试钉住。

### 3.2 详情页从「一段摘要」变成「完整的旅行」

现在 `/circle/<id>` 只有：封面、标题、日期、一句摘要、作者、赞/评/藏、照片墙。别人点进去**看不到「旅行」本身**——这正是「没办法点开别人的旅行记录去看」的实质。

改为按天呈现（数据侧 `getSocialPost` 已经拿到 `travelId`）：

- `GET /api/social/posts/[id]` 增加 `days: [{ date, title, summary, itinerary: [...], photos: [...] }]`、`canSuggest`
- 权限：只返回 `visibility = 'PUBLIC'` 或 `isPublic = true` 的旅行下的天/回忆/照片与行程；私密内容一律不下发（沿用 `social-permissions.ts` 的口径，**不新造第二套判定**）
- 详情页新增：「按天回顾」章节流（复用 `components/travel/TravelTimeline.tsx` 的渲染样式，但**只读态**），每天显示日期、行程胶囊（景点/餐厅/住宿…）、回忆正文、照片缩略图
- 底部保留「查看完整旅行记录 →」跳 `/travel/<slug>`（作者自己的或完整权限时），别人只看公开部分

### 3.3 分享（当前完全缺失）

- `SocialBar` 增加第 4 个动作「分享」：
  - 优先 `navigator.share`（安卓壳/移动浏览器原生分享面板）
  - 不支持时 → 复制链接（`/circle/<id>`）并 Toast 提示
  - 长按/更多菜单里给出「生成分享图」（**本轮先不做**，只留位，见 §6）
- 详情页 SEO/预览：`generateMetadata`（服务端）给出标题 + 封面，分享到微信/iMessage 有卡片预览。注意 `/circle/[postId]/layout.tsx` 现在只有 `generateStaticParams`，要补 metadata 且**不能破坏静态导出**（移动壳构建会排除 `app/api`，页面仍要能静态生成）。

### 3.4 短名单研究结论（用于这一轮的具体做法）

> 详细版见本节末尾「参考实现」表。

- **详情页「按天章节」的信息层次**：参考开源旅行日志项目的 trip detail（`day → activities → photos` 三段式），而不是社交媒体式「大图 + 正文」。这也是我们已有 `TravelDay/ItineraryItem/Memory` 模型的自然表达。
- **卡片点开 → 详情页的加载体验**：参考开源社交/Feed 项目普遍采用的「骨架屏 + 封面乐观渲染」，避免整页 spinner。
- **分享入口位置**：参考 `opencollective` 风格的行内动作条（赞/评/藏/分享四个等权重图标），而不是藏在溢出菜单里。

### 3.5 验收

- [ ] 游客（未登录）在 `/circle` 能看到公开旅行并点进 `/circle/<id>`，内容可读
- [ ] 登录用户点任意卡片都进详情页；URL 不变形；无 JS 报错
- [ ] 详情页在弱网（DevTools Slow 3G）下首帧有内容，不是空白转圈
- [ ] 详情页能看到「按天」的完整行程与照片；私密回忆/照片**不出现**（用另一个账号验证）
- [ ] 分享按钮在安卓壳触发原生分享、在桌面浏览器复制链接
- [ ] `tests/e2e/circle-open.spec.ts` 通过；`vitest` 里新增接口权限单测（公开可见 / 私密不可见）

## 4. 第三轮：旅行空间（情侣 / 闺蜜 / 家人 / 朋友）

### 4.1 现状：后端有 80%，前端只有 20%

已有：`Space`（含 `spaceType`）、`SpaceMember`、`SpaceInvite`、邀请码生成/加入/移除成员/退出空间（`/api/spaces/*`）、一个弹窗式 `SpacePanel`。

缺口（按重要性）：
1. **创建空间时没地方选类型**：`SpacePanel` 创建表单只收名称+简介，`spaceType` 永远是 schema 默认的 `COUPLE` → 「家人空间/闺蜜空间」根本建不出来。
2. **没有空间详情页**：`SpacePanel` 是弹窗，只显示「成员数/旅行数/相册数/回忆数」四个数字 + 成员列表，放不下「一起记录的旅行」和「正在规划」。
3. **空间成员看不到彼此的旅行**：读路径用 `scopedWhere(userId,'ownerId')`（`lib/modules/travel/travel.service.ts:100`），只认 `ownerId`。空间旅行（`spaceId` 非空、`ownerId` 是别人）对成员不可见。`canViewResource`（`lib/modules/access/index.ts:59`）已经支持 `visibility='SPACE'` + 活跃成员，但 `listTravels` 没走它。
   - 具体表现：A 和 B 在同一个空间，A 建了旅行（默认 `visibility='SPACE'`），B 打开 `/travel` **看不到它**；而 B 直接打开 `/travel/<slug>` 又能看到（详情走的是 `canViewResourceById`）。列表与详情口径不一致，这是这条 bug 的特征，容易误判成"同步丢了"。

### 4.2 方案

| # | 改动 | 位置 |
|---|---|---|
| 1 | 创建空间表单加类型选择（情侣/家人/朋友/闺蜜/其他，2 列网格 + 一句说明，沿用新建旅行里已验证的 `TRAVEL_TYPE_OPTIONS` 交互）；创建接口接受 `spaceType` | `components/space/SpacePanel.tsx`、`app/api/spaces/route.ts`、`lib/modules/space/space.service.ts` |
| 2 | 新增 `/space/[slug]` 空间详情页（取代弹窗）：头图 + 空间名 + 成员头像堆叠 + 「邀请」按钮（邀请码/链接，复用已有接口） | 新增 `app/space/[slug]/page.tsx` + `components/space/SpaceDetail.tsx` |
| 3 | 空间页三段内容：**一起记录的旅行**（成员可见的旅行卡）、**正在规划**（`status=PLANNED` 且日期在未来）、**成员与邀请**（从弹窗迁过来） | 同上 |
| 4 | `listTravels` 增加空间可见性：`ownerId = me` OR `spaceId ∈ 我的 ACTIVE 空间`（同一套 `access` 判定，不新造逻辑）；`/travel` 列表加「空间旅行」分组或角标 | `lib/modules/travel/travel.service.ts` + `lib/modules/access/index.ts` |
| 5 | 「我的」页新增「我的空间」卡片区（§2.4 第 2 段），点进空间页 | `components/social/MeHome.tsx` |

> **不需要新建任何表**。空间相关的表在 schema 里已经齐了，这一轮本质是「把已有后端接出来 + 补一个类型字段 + 补空间可见性读路径」。

### 4.3 关于「空间里的旅行也走公开/私密逻辑」

复用现有三档，不新增枚举：
- `PRIVATE` 仅自己
- `SPACE` 空间成员可见（**默认**）
- `PUBLIC` 公开到旅行圈（`syncTravelPost` 会同步出公开帖，已有逻辑）

关键：把这三档做成**旅行详情页上的一个显式控件**（现在「编辑信息」抽屉里没有这项！`TravelInfoEditor.tsx` 只有标题/目的地/日期/描述），否则用户根本设不了「公开」。这一条同时是 §5 的前提。

### 4.4 验收

- [ ] 能创建「家人空间」，并在「我的」看到入口；A 建空间 → 生成邀请码 → B 加入（真机两个账号走一遍）
- [ ] B 加入后能在空间页看到 A 用 `SPACE` 可见性发布的旅行；把该旅行改 `PRIVATE` 后 B 不再看到
- [ ] 非成员访问空间页 → 明确无权限提示，不泄露成员与旅行
- [ ] `/travel` 列表对空间旅行的显示不重复、不丢失（A 的私人旅行不出现在 B 的列表）

## 5. 第四轮：规划下一次旅行 + 参考建议

### 5.1 核心决定：**复用 `TravelPost` 的评论系统，不新建「建议表」**

理由：
- 现有的 `TravelPost` + `Comment` + `PostLike` + `PostFavorite` + `Notification` + 举报/审核（`lib/modules/social/moderation.service.ts`）已经是一套完整的「内容 + 讨论 + 互动 + 治理」，**再建一套 `TripSuggestion` 等于把评论、点赞、通知、审核全部重写一遍**；
- 但有一个坑必须处理：`TravelPost` 的 `travelId` 是 `@unique`，feed 的 `baseWhere = { visibility: 'PUBLIC' }`，也就是说**一旦给规划中的旅行建了公开帖，它就会混进旅行圈的「最新/推荐」**，语义错误（「我要去大理，求建议」不该出现在游记流里）。

所以：给 `TravelPost` 加一个 **`kind` 字段**（`JOURNAL` | `PLAN`，默认 `JOURNAL`），然后：
- 旅行圈 feed：`kind = 'JOURNAL'`（+ 新增一个「求建议」tab，可选）
- 计划详情：`kind = 'PLAN'`，公开可见，讨论区标题为「参考建议」，点赞语义为「这个想法不错」
- 规划旅行的 `visibility` 可以是 `SPACE`（只有空间成员看得到，讨论仅成员）或 `PUBLIC`（旅行圈可见，谁都能建议）——这正好对上你说的「规划下次旅行可以选择公开或私密」

### 5.2 前端流程

**空间页「正在规划」** → `一起规划下一趟` → 复用 `TravelComposerForm`（已支持目的地/日期/标题）但**建出 `status = PLANNED` 的旅行**，并带 `spaceId`：

`components/travel/TravelComposerForm.tsx` 加一个 `planMode` 变体（标题改「规划下一趟」、按钮改「建好，喊大家来出主意」、隐藏「已去过」相关文案）。

**计划详情页**（`/travel/<slug>`，`status=PLANNED` 时渲染成计划态）：
```
┌ 下一趟计划 · 大理 5 天 ────────────────┐
│ 日期区间 · 谁发起的 · 可见性（空间/公开）│
├ 想去的地方（可直接加行程项，复用 ItineraryEditor）┤
├ 大家的建议（复用 CommentPanel 列表 + 输入框）  │
│   · 「去过洱海，下午光线最好」  — 小明       │
│   · 「这个想法不错 👍」                      │
├ [ 我也给点建议 ]  [ 分享给朋友 ]             │
└────────────────────────────────────┘
```
- **去过的人也来给建议**：不是新机制，而是 §3.3 的分享链接 + 评论；再加一个轻量钩子——如果评论者自己的旅行里有同城市（`Travel.location` 相同），评论框上方提示「你也去过大理，说说你的经验吧」，这是他最初那句「如果自己也去过，也能给出一些建议」的落点。
- **谁能建议（已拍板）**：`visibility='PUBLIC'` 的计划 → 任何**登录用户**都能评论；`visibility='SPACE'` 的计划 → **仅空间成员**能评论（非成员连内容都看不到）。判定放在服务端 `createPostComment` / `listPostComments`，不在前端藏按钮了事。

### 5.3 通知

复用 `Notification`（`NotificationType` 已有 `COMMENT`/`LIKE`/`SYSTEM`）。建议进来时通知计划发起人；`enum` 不新增（避免又一趟迁移），用 `refType = 'TravelPost'` 区分。

### 5.4 数据改动（最小集）

```prisma

  // ...
  kind TripPlanKind @default(JOURNAL)   // 新增
}
enum TripPlanKind { JOURNAL  PLAN }
```

DDL 走 `scripts/apply-schema-migration.cjs`（幂等检查列是否存在）。**不新增表。**

### 5.5 验收

- [ ] 空间里能发起一趟「未来旅行」，默认 `SPACE` 可见；成员都能看到
- [ ] 成员可加「想去的地方」与「建议」；发起人收到通知
- [ ] 把计划改成公开 → 旅行圈里能搜到/看到它，但**不出现在「最新」游记流**（`kind=PLAN` 隔离）
- [ ] 计划完成后把 `status` 改成已完成，公开后作为游记出现在旅行圈
- [ ] 别人（非成员）对公开计划能评论；对空间计划看不到内容（权限单测覆盖）

### R1 头图的两处设计更新（来自调研报告，直接吸收）

**① 头图必须叠一层暗色蒙版**（`notus-nextjs` MIT 的做法）：用户上传的风景照亮度不可控，若把名字/按钮直接压在图上，浅色照片会让白字彻底消失。做法是图上叠 `bg-black/50`（我们实际用暖色暗调 `linear-gradient(to top, rgba(0,0,0,.55), transparent 60%)` 更贴合行迹的暖色系），下半部再让不透明卡（含头像/名号/统计）压上来。**统计与名字一律在卡内、不在图上**，这是 §2.3 就定下的原则，蒙版是给图上的两个小动作（编辑资料 / 换头图）兜底。

**② 头图支持用户自选焦点**（`LycheeOrg/Lychee` MIT 的做法）：风景横幅照直接 `object-cover` 居中有很大概率把主体（人、地标）裁掉。做法是存两个 float（`coverFocusX` / `coverFocusY`），渲染时算

```
object-position: ((focusX * -1 + 1) * 50)% ((focusY * -1 + 1) * 50)%
```

无值时回落 `center`。选择器做成上传后的一个 3×3 九宫格（比引入 npm `image-focus` 更省事、也不必新增依赖），点击即预览、随头图一起保存。代价是 `User` 上多两列 `coverFocusX/coverFocusY`（`Float?`），收益是「我上传的照片脸没被裁掉」——这是最容易被投诉、又最容易避免的一类问题。

> 这两条都只改 R1 的 `ProfileHero.tsx` + `app/api/me/cover/route.ts` + 两个 schema 列，不扩大风险面。

### 10.3 后续排期可用的具体做法（本轮不做，但记下来）

- **行程页数据契约（R4 直接对着它定字段）** — `zexuanw958-svg/travel-plan-viz`（MIT）`assets/page-contract.md`：
  `preTrip{ weather{summary,typhoon}, packing, payment, apps[], ticketTip }`、`flights.booked` **vs** `flights.candidates`（带机型/直飞或经停/价位区间）、`hotelAreas[{area, reason, options[{tier, priceRange}]}]`、`days[].slots[] = { period: morning|noon|evening, needsBooking, leadDays }` → `reminders=[{item, leadDays}]`（出发前 N 天提醒）。
  **⚠️ 里面有对我们（用高德/腾讯地图坐标）的刚需**：契约明确要求坐标统一 **WGS-84**，高德/腾讯返回的是 **GCJ-02**，必须先 `gcj02ToWgs84` 再入库。我们行程项目前**没有坐标字段**，R4 加坐标时必须带上这个转换，否则地图整体偏移几百米。
  同仓库 `references/design-guidelines.md` 的图片规范也值得抄：**容器固定比例 + `<img>` `object-fit:cover` + `display:block`（推荐 `position:absolute; inset:0`）**，严禁变形。
- **按 Day 分组的时间轴（R4）** — `wang-bool/Travel-Story`（MIT）`components/PlanTimeline.tsx`：`DAY {String(day).padStart(2,'0')}` 等宽零填充 + 日期等宽灰字；同 Day 内拖拽排序 + 跨 Day 移动；每天底部 `+ 添加地点`；数据用 `stopsByDay: Map<dayId, TripStop[]>`。
  同仓库 `app/trip/[id]/page.tsx` 有一条**工程原则值得抄**：路线异步获取后**只有 authoritative 的路线才持久化**，兜底直线不落库（"避免在规划图上画出误导性直线"）。
- **通关护照印章墙** — `linkingoscar/footprint`（MIT，但**仅 3★**，模块描述**来自 README、未读实现**，当设计说明书看）：每座到访城市一枚海关戳（城市三字码 PEK/SHA/HGH + 中英地名 + 首次入境日期 + 等宽经纬度 + 微倾斜印泥质感 + 复古羊皮纸内页）。我们已有 `TravelStarMap` / `china-map` 基础，做这个成本不高，是「旅行档案」的强记忆点。
- **1 / 4 / 9 宫格自适应排版** — 同上 `MosaicEngine`：1 图画卷 / 4 图田字格 / 9 图九宫格，**超 9 张自动 `+N` 遮罩 + `📷 N图` 角标**。我们的照片网格目前是等分方格，这是升级方向。
- **录入效率** — 同上 `QuickCatch`：全局 `Ctrl+V` 粘贴导入、拖入照片读 **EXIF GPS** 逆地理回填地点、自动拟标题、多行 URL 批量导入。安全侧也值得核对：`/uploads/<file>` 做 owner 级校验，URL 里只用**短期限 media token**、禁止塞主 JWT（防浏览器历史/日志泄漏）—— 我们已有 `/api/uploads/[...path]`，值得复核一遍。
- **按年份切片的足迹时间轴** — `Aisland-SJL/StarMap`（MIT，中文，Cesium 3D 地球）：组件文件名已核实（`Timeline.tsx` / `JourneyYearCards.tsx` / `AtlasGlobe.tsx`），但**未逐行读实现**。Cesium 体积大；只要 2D 足迹图的话我们现有 `china-map` 够用，不值得为它引 Cesium。
- **`itskovacs/trip`**（POI 地图 + 多日行程 + 同行者协作，定位与我们几乎重合）：**许可证未核实通过** —— API 报 MIT，但 `LICENSE` / `LICENSE.md`（main）均 404，且未能枚举源码目录（API 速率限制 403、jsDelivr 404）。**抄之前必须先自行确认许可证文件。**
- **非开源但对标的形态**：小红书（双列瀑布流、封面 3:4、详情页底部固定「赞/藏/评」三键 + 图片轮播 `1/9` 页码）、圆周旅迹（以「天」为单元，**景点之间显式显示交通方式与耗时**、地点可标「想去/已去」）、TimeTree（共享日历 = 我们的空间，成员专属颜色 + 事件评论 + 链接/邮箱邀请）、TripIt（**粘贴订单文本自动解析成行程条目**，分 upcoming/past）、Notion 旅行模板（**视图切换 + 状态属性** Planning/Booked/Visited）。

### 10.4 许可证硬规则（写进团队约定）

1. 只从 **MIT / Apache-2.0 / BSD** 的仓库复制代码；**GPL / AGPL 一行都不复制**（只读交互与数据模型）。
