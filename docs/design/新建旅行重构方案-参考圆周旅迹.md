# 新建旅行模块重构方案（参考圆周旅迹）

> 触发：真机反馈「新建旅行界面和交互太粗糙」，要求参考圆周旅迹（圆周旅迹 / com.chaochaoshishi.slytherin）。
>
> 本文档 = 现状审计 + 参考产品拆解 + 数据模型可行性判断 + 分阶段实施方案。
>
> 相关文件：`components/travel/TravelComposer.tsx`(443 行)、`app/travel/new/page.tsx`、
> `lib/modules/offline/travel-write.ts`、`app/api/admin/travels/route.ts`、
> `prisma/schema.prisma`(Travel / TravelDay / ItineraryItem)。

---

## 0. 先修正一个前提（请先看这一节）

你说「直接照抄它的 UI 设计和交互就可以了」。**交互模式我会照搬，但像素级界面不能照抄**，原因不是保守，是三条硬事实：

1. **它是「行程规划器」，我们是「旅行记忆册」。** 它的主循环是
   `抄攻略 → 排每日行程 → 地图导览`（行前）；我们的主循环是
   `记旅行 → 传照片 → 生成画册`（行后）。把它的界面整块搬过来，会出现
   「建完旅行让你去排景点，但你要的是记录回忆」的错配。
2. **两套设计系统不同。** 它是 `#4DA6FF` 蓝 + 大圆角卡片 + 地图为底；
   我们全站是暖陶土 `travel.*` + 米白纸感（`docs/design/travel-notes-design-skill.md` 是唯一 UI 规范来源，
   且明文禁止「游戏 UI / 强霓虹 / 复杂渐变」）。照抄会把画册、旅行圈、碎碎念的视觉一致性打碎。
3. **它可以为了抄而抄，我不能。** 我是照着参考产品的交互逻辑重写实现，
   不复制其代码与素材 —— 这与前面相册重构对 `create-photo-flipbook-ui` 的处置一致。

**所以我做的是**：把它**真正好的交互模式**（信息层级、输入顺序、日期选择、底部操作条、空态）
逐条拆出来，用我们的 token 和组件重实现。视觉上你会看到"同样的顺手"，但配色和质感仍是行迹的。

## 1. 现状审计：粗糙在哪（逐条对照代码）

| # | 问题 | 位置 | 为什么算"粗糙" |
|---|---|---|---|
| 1 | **必填只有「旅行名称」，但没给任何起名帮助** | `TravelComposer` 表单第一项是裸 `input`，placeholder「旅行名称（必填）」 | 用户面对空白框要想名字。参考产品是「目的地 + 日期」先定，标题自动长出来 |
| 2 | **目的地完全缺失** | 表单无目的地字段；`createTravel` 甚至硬写 `location: null`（`travel-write.ts:46`） | 旅行最自然的标识是"去哪"，我们连录入口都没有。且**画册生成靠 `location` 匹配城市**（`travel-book.service.ts` 用 `findCityByName`），为空就退化成"标题当城市" |
| 3 | **日期用两个原生 `<input type="date">`，没有天数** | 开始/结束并列两个系统日期控件 | 原生控件在安卓 WebView 里样式不可控、点击区域小；且**不显示"共几天"**，用户不知道结束日选对没有 |
| 4 | **没有开始/结束日期的合理性校验** | `endDate < startDate` 也能保存 | 直接产出负数天数的旅行 |
| 5 | **旅行类型是 7 个胶囊挤在 4 列里** | `flex flex-wrap gap-2`，纯文字、无图标、无说明 | 「闺蜜/兄弟」「结伴」这种标签光看字不知道差别；触控目标偏小 |
| 6 | **同行者输入是"姓名 + 关系 + 添加"三个控件一行** | 两个输入框 + 按钮横向排，窄屏很挤 | 加一个人要点三次、敲回车；且没有"常用关系"快捷选项，每个都要现打 |
| 7 | **表单一次性摊开 5 个区块** | 名称/描述/类型/同行者/日期平铺 | 必填项（名称）和可选项（描述、同行者）视觉权重相同，首屏很"重" |
| 8 | **没有"更多选项"收纳** | 描述、同行者与必填项同级 | 参考产品的做法是核心 2-3 项 + 折叠区 |
| 9 | **提交后才 1.2 秒自动跳回列表** | `setTimeout(..., 1200)` 后 `setOpen(false)` | 用户第一反应是"我刚建的旅行呢"，还要自己去列表找；参考产品是**建完直接进详情** |
| 10 | **成功/失败提示是行内小字** | `text-xs` 的一行 `<p>`，绿色/红色 | 离提交按钮远、易被忽略；离线时"已保存到本地"这种重要信息不该这么轻 |
| 11 | **无草稿保留** | 组件卸载即丢 | 填一半切走（尤其是选照片中）全丢 |
| 12 | **无"公开/私密"感知** | 表单没这项，默认 `isPublic=false` | 用户不知道新建的旅行是私密的 |
| 13 | **顶部是 26px 粗体标题 + 一行说明** | `text-[26px] font-bold` | 信息密度低，浪费一整块首屏；参考产品顶栏是**标题 + 日期副标题 + 操作**三合一 |

## 2. 参考产品拆解（只取交互，不取视觉）

> 来源：App Store 官方介绍 + 应用商店截图的界面观察。以下只记录**可迁移的交互模式**。

### 2.1 它的界面骨架（截图实证）

**行程详情页**（截图：内蒙古旅游）：
```
┌──────────────────────────┐
│ ✕                    10  ⋯│  ← 顶栏：关闭 / 视图切换 / 更多
│ 内蒙古旅游                │  ← 大标题（旅行名）
│ 10.3 至 10.5 3日2晚       │  ← 日期 + 自动算出的天数
├──────────────────────────┤
│ (10.3 周五) 10.4 周六 10.5 周日 未计划 │ ← 日期胶囊：可横滑、含"未计划"
├──────────────────────────┤
│ 10.3 周五                 │  ← 分组标题
│  ✈  前往 上海虹桥T2        │
│     12:00 — 14:00         │
│  ⛰  成吉思汗广场           │  ← 地点 + 时间
│     14:00 — 15:00         │
│  ⛰  呼伦贝尔古城           │
│     14:00                 │
│     本地人都很喜欢的餐馆…   │  ← 备注（小字灰）
│  ＋ 添加行程               │  ← 行内追加
└──────────────────────────┘
                    [◉ 地图]   ← 右下悬浮主操作
```

**空态页**：只有一行居中小字 **「还未添加行程」** —— 不画插画、不给大按钮，
因为"添加行程"在上一屏的行内 `＋` 已经给了。**这是最值得抄的一条**。

**它的"新建"实际入口**：AI 输入框
`「帮我规划新加坡3日行程」` + 下方快捷建议（`附近有什么好玩的地方?` / `帮我把第一天轻松一些`）。
它的新建**不是一张表单**，而是「说一句话 → 生成」。

### 2.2 可迁移的 8 条交互模式（本方案的取材范围）

| # | 模式 | 我们的落法 |
|---|---|---|
| M1 | **目的地 + 日期 是最先确定的两个锚点**，标题可由它们派生 | 顺序改为 目的地 → 日期 → 名称（带自动建议） |
| M2 | **日期区间选择器一处定完，实时显示「共 N 天 M 晚」** | 自研区间选择（不引依赖），副标题实时回显 |
| M3 | **日期胶囊横滑，含「未计划」容错项** | 用于旅行详情页的 DAY 导航（阶段 2） |
| M4 | **时间轴式条目：图标 + 标题 + 时间 + 备注** | 用于行程条目（阶段 2），复用我们已有的 `ItineraryItem` |
| M5 | **行内 `＋ 添加` 追加，不用弹窗** | 同行者、行程条目都改成行内追加 |
| M6 | **空态极简**：一行字，不做插画 + 大按钮 | 替换我们现在的空态 |
| M7 | **建完直接进详情**，不跳列表 | `onCreated` 改为 `router.replace('/travel/<slug>')` |
| M8 | **右下悬浮主操作**（地图） | 建完后的主操作改为「上传照片」（我们的主循环） |

**刻意不抄**：蓝色主题、大圆角卡片风格、地图作为首屏底、AI 对话式新建（那是它的护城河，也是另一个量级的产品决策）。

## 3. 数据模型：比你预想的更有利

**结论：阶段 1 与阶段 2 都不需要改 Prisma schema。** 现成字段：

| 我们要做的 | 现成字段 / 表 | 状态 |
|---|---|---|
| 目的地 | `Travel.location` (`VarChar(255)`) | **已存在**，但 `createTravel` 硬写 `null`，且 `/api/admin/travels` 未确认接收 |
| 日期 + 天数 | `Travel.startDate` / `endDate` | 已存在且已传 |
| 同行者 | `Travel.companions` (Json) | 已存在且已传 |
| 旅行类型 | `Travel.travelType` (enum) | 已存在且已传 |
| **每日行程时间轴** | `TravelDay` + `ItineraryItem` | **已存在**（后端 admin 已在用），前台无 UI |
| 地点库 / 经纬度 | `Location` (name/address/city/lat/lng) | 已存在 |
| 城市规范化（画册匹配） | `data/cities.ts` 的 `findCityByName()` | 已存在 |
| 照片 | `Media` + `Memory` | 已存在 |

**所以阶段 1 是纯前端 + 一个字段打通**，改动面比相册重构小一个量级。

需要打通的三个点（都很小）：
1. `lib/modules/offline/travel-write.ts`：`CreateTravelInput` 加 `location?`；原生壳分支的 `location: null` 改为 `input.location || null`。
2. `app/api/admin/travels/route.ts`（POST）：确认/补上 `location` 的接收与校验。
3. 原生壳 SQLite 的 `travel` 表需有 `location` 列（`lib/modules/offline/schema.ts` 确认；已有 `location` 字段映射的先例）。

## 4. 分阶段方案

### 阶段 1 · 新建旅行表单重做（纯前端，1-2 天）

**目标：把「填表格」变成「确认三个锚点」。**

#### 4.1 新信息架构（移动端全屏页）

```
┌────────────────────────────────────┐
│  ←              新建旅行            │  顶栏：返回 + 居中标题 + （无多余动作）
├────────────────────────────────────┤
│  去哪？                             │  ① 目的地（首个焦点，自动弹键盘）
│  📍 乌鲁木齐            [选城市 ▾]  │     输入时从 data/cities.ts 联想
├────────────────────────────────────┤
│  什么时候？                          │  ② 日期区间
│  ┌──────────┐  ┌──────────┐        │
│  │ 2026.08.14│  → │ 2026.08.19│    │     点任一侧弹同一个区间选择器
│  └──────────┘  └──────────┘        │
│  共 6 天 5 晚 · 8月14日 周五出发     │     ← 实时回算（M2）
├────────────────────────────────────┤
│  给这段旅程起个名字                  │  ③ 名称
│  [ 新疆 6 日 ]                      │     ← 由目的地+天数自动建议（M1）
│  💡 换个说法： 新疆之行 / 2026 新疆   │     ← 可点选替换
├────────────────────────────────────┤
│  ▾ 更多（可选）                      │  ④ 折叠区（M6 的收纳思路）
│  ┌ 这次旅行是？ ────────────────┐   │
│  │ [🧍独旅] [💑情侣] [👨‍👩‍👧家庭]    │   │     2 列网格 + 图标 + 一句说明
│  │ [👥朋友] [🤝结伴] [✨其他]    │   │     （修问题 5）
│  ├ 和谁一起 ──────────────────┤   │
│  │ [姓名____] ＋               │   │     单输入框 + 行内追加（M5）
│  │ 常用：爸爸 妈妈 老婆 老公 朋友 │   │     一键加（修问题 6）
│  │ (已添加的胶囊，可删)         │   │
│  ├ 一句话描述 ────────────────┤   │
│  │ [多行文本]                  │   │
│  ├ 可见性 ───────────────────┤   │
│  │ ● 仅自己  ○ 公开            │   │     默认私密，明确告知（修问题 12）
└────────────────────────────────────┘
│         [  开始记录  ]              │  底部固定操作条（含键盘避让）
└────────────────────────────────────┘
```

#### 4.2 逐条修复映射

| 原问题 | 修法 |
|---|---|
| 1 起名困难 | 目的地/日期变化时生成 2-3 个候选标题，一键采用；用户手动改过后停止建议 |
| 2 无目的地 | 新增目的地输入 + `data/cities.ts` 联想下拉；写入 `Travel.location` |
| 3 原生双 date | 自研区间选择（底部抽屉 + 月历），一处定完；**不引依赖** |
| 4 无校验 | `endDate < startDate` 时禁用提交并内联提示；同日按 1 天 0 晚 |
| 5 类型胶囊 | 2 列网格：图标 + 名称 + 一句说明（如「结伴 · 多人拼团出行」），选中态用 `--m-accent` |
| 6 同行者繁琐 | 单输入框 + `＋`；回车即加；4 个常用关系快捷 chips；已添加项行内可删 |
| 7 一次摊开 | 必填 3 项在上，其余收进「更多（可选）」折叠 |
| 8 无收纳 | 同上；折叠区默认收起但**显示已填摘要**（如「更多 · 情侣 · 2 位同行」） |
| 9 建完跳列表 | `onCreated` → 进该旅行的详情页（M7）；原生壳离线时先进本地详情 |
| 10 提示太轻 | 提交结果用 Toast（已有 `components/mobile/Toast`）+ 失败时保留已填内容 |
| 11 无草稿 | 表单值写 `sessionStorage`，返回时恢复（不做跨设备草稿） |
| 12 无可见性 | 折叠区里给「仅自己 / 公开」单选，默认仅自己 |

#### 4.3 交互细节（决定"手感"的部分）

- **首屏焦点**：进页面自动聚焦目的地，键盘弹起即输入 —— 参考产品那种"打开就开始"的轻盈感。
- **键盘避让**：底部操作条 `position: sticky` + `env(safe-area-inset-bottom)`；输入框聚焦时按钮上移（复用 `components/mobile/BottomSheet` 的既有避让逻辑）。
- **触控目标**：所有可点元素 ≥44px（对齐 `docs/design/移动端设计规范.md`）。
- **错误就近**：校验提示贴在被校验控件下方，不用顶部汇总条。
- **动效**：仅"已添加项进入"用 150ms 淡入+位移；尊重 `prefers-reduced-motion`。
- **提交态**：按钮内联 spinner + 文案变「正在创建…」；成功后按钮短暂变 ✓ 再跳转。

#### 4.4 空态（M6）

详情页无行程时，一行居中：
```
还未添加行程
```
不放插画、不放按钮（追加入口在行内 `＋`）。这一条直接对齐参考产品。

### 阶段 2 · 轻量行程编排（前端为主，2-3 天）

**目标：建完旅行后，"这段旅程有什么"可被轻量安排，并直接喂给画册。**

- 详情页按 `TravelDay` 渲染**日期胶囊横滑**（M3）+ **时间轴条目**（M4）：
  `图标 + 标题 + 起止时间 + 地点 + 备注`，行内 `＋ 添加行程`。
- 复用**已有的** `TravelDay` / `ItineraryItem` 表与 admin 接口，前台补 UI。
- 与画册联动（免费收益）：画册的 `DAY_OPENING` 页已经在渲染 `chapter.itinerary`
  （`lib/modules/album/book/composer.ts` 读 `day.itinerary`），**行程一旦填了，画册日程页立刻有内容**。
- 空态沿用 M6 的单行样式。

### 阶段 3 · 暂不做（记录为决策）

| 能力 | 为什么现在不做 |
|---|---|
| 链接/图片智能解析攻略（抄作业） | 需要 LLM 调用 + 解析管线 + 付费成本，是独立项目级投入；且与"记忆册"主线弱相关 |
| AI 对话式新建行程 | 同上；且它需要"可编辑行程"这个前提，我们阶段 2 才刚有 |
| 多人协同编辑 | 需要邀请/权限/实时同步（我们只有 Space 成员模型），成本高、与个人记忆册定位不符 |
| 地图导览 / 路线规划 | 我们已有 `components/china-map` 与 `TravelStarMap`；行程级路线属另一条线，不塞进本次 |
| 天气/交通补全 | 依赖第三方数据源与时延，收益/成本不划算 |

## 5. 验收标准

**功能**
- [ ] 目的地可输入并从城市库联想；保存后 `Travel.location` 有值
- [ ] 画册自动匹配到正确城市（`findCityByName` 命中，而不是退化成"用标题当城市"）
- [ ] 日期区间一处选完；实时显示「共 N 天 M 晚」
- [ ] `endDate < startDate` 无法提交，并有就近提示
- [ ] 标题建议可一键采用；手动修改后不再被覆盖
- [ ] 同行者：输入 + 回车即添加；常用关系一键添加；行内可删
- [ ] 类型选择为 2 列网格，含图标与说明
- [ ] 「更多」折叠区含描述/类型/同行者/可见性，且收起时显示已填摘要
- [ ] 建完直接进该旅行详情页（不是列表）
- [ ] 表单中途返回再进来，内容还在（sessionStorage 草稿）

**体验**
- [ ] 进页面自动聚焦目的地，键盘弹起
- [ ] 底部操作条在键盘弹起时不被遮挡
- [ ] 所有可点元素 ≥44px
- [ ] 提交中/成功/失败三态清晰，失败不丢已填内容
- [ ] `prefers-reduced-motion` 下无位移动效
- [ ] 390px 与 360px 无横向溢出（复用现有 E2E `geometry.spec.ts` 的断言方式）

**回归（不得破坏）**
- [ ] 离线写路径仍可用（原生壳写 SQLite + 入同步队列）
- [ ] `/api/admin/travels` 的既有调用方（后台新建旅行）不受影响
- [ ] 旅行列表/地图/看板/画册统计口径不变
- [ ] `tests/e2e/interact.spec.ts`「新建旅行（标题+类型）→ 列表可见」继续通过
  （注意：阶段 1 改了创建后跳转目标，该用例需同步调整 —— 我会在实现时一并改）

## 6. 落地顺序与工作量

| 步骤 | 内容 | 预估 |
|---|---|---|
| 1 | 打通 `location` 写入（前端 input → offline write → API → DB）+ 单测 | 0.5 天 |
| 2 | 表单骨架重排（目的地/日期/名称 + 更多折叠） | 0.5 天 |
| 3 | 区间日期选择器（含天数回算 + 校验） | 0.5 天 |
| 4 | 标题建议 + 同行者行内追加 + 类型网格 | 0.5 天 |
| 5 | 提交态/Toast/草稿/建完跳详情 + 键盘避让 | 0.5 天 |
| 6 | E2E 补充（新建全流程、日期校验、草稿）+ 调整既有 interact 用例 | 0.5 天 |

阶段 1 合计约 **3 天**（含测试），可独立上线、可回滚。

## 7. 需要你拍板的三点

1. **目的地字段**：用现成的 `Travel.location`（不改 schema，推荐）？
   还是新增独立的 `destination` 字段（更语义化但要迁移）？
2. **建完去哪**：直接进该旅行详情页（推荐，对齐参考产品）？还是保持回列表？
   ⚠️ 若选前者，需要**同时决定**详情页在没有照片时是否足够好看（否则落地页很空）。
3. **阶段 2 要不要一起排**：只做阶段 1（表单变好用），还是连行程编排一起做？
   我的建议是**先只做阶段 1 并真机验证手感**，确认对了再做阶段 2 —— 避免一次性堆叠两处改动后难以定位问题。
