### 0.4 最大风险点（三个，按严重度排序）

**风险一：认证/授权体系停留在「单用户时代」，形成零门槛账号接管链（🔴 最高优先）。**
三处旧假设叠加：①相册令牌与登录会话共用同一 JWT 密钥与 issuer，且**没有 sid/username 也能通过 requireAuth**（lib/album-auth.ts:9-17 + lib/auth-middleware.ts:34-51）；②POST /api/admin/force-change-password 只校验登录、不校验旧密码/能力位，直接改 id 最小的用户（app/api/admin/force-change-password/route.ts:16-37 → lib/auth.ts:201-221）；③能力模型把「没有任何 Space 成员身份」判成 OWNER（lib/modules/space/permissions.ts:153），而 /api/register 公开。结果是：**攻击者无需账号（拿到相册令牌）或注册一个账号，即可改掉站长密码、踢掉其全部会话，或读全站审计、下架/封禁他人内容**。三条链只需修通一条即可接管，必须一起收口。

**风险二：发布链路没有强制门禁，数据库没有迁移历史（🔴）。**
Dockerfile:13 写死 SKIP_TSC=1、next.config.js:23 构建期跳过 ESLint、scripts/server-rebuild.sh 只做「清盘→解包→重建→curl || true」、docker-entrypoint.sh:12-16 每次启动跑手写 ALTER + prisma db push 且失败吞掉后继续启动。CI 里的 lint（485 warning 全过）、npm audit（43 个漏洞，24 high，|| true）、E2E（21 spec 不进 CI）都不阻断。**一次「本地改完直接打包上线」即可让类型错误进生产；一次重启即可静默改表，且回滚无镜像 tag 可依。**

**风险三：首屏策略与 App Router 能力背道而驰，性能债与「流畅/原生感」目标互相拉扯（🔴/🟡）。**
48 个 page.tsx 中 34 个 'use client'；首页/相册/看板首屏分别付 **240KB / 417KB / 470KB gz JS**（实测 .next 产物），其中 132KB three.js、193KB 中国 GeoJSON 可立刻拿掉；全仓 0 个 loading/error/not-found、0 个 generateMetadata。移动端 26.3MB APK 中 DEX 5.18MB（未开 R8）+ 4 ABI SQLCipher 7.27MB（x86 占 4.27MB）+ 6.85MB 像素字体，均未裁剪。

## 2. 逐模块评审结果

### 2.1 模块一 · 系统架构

**结论**：分层是真实落地的，不是「目录假装分层」；但架构处于「单用户博客」到「多用户社交产品」的迁移中途，身份/权限/数据演进三块都有两代实现并存。

#### A-1 🔴 单用户假设与多用户模型并存（本次评审的主线风险）
- **位置**：lib/modules/space/permissions.ts:146-163、lib/auth.ts:170,204,225、lib/services/site-service.ts:16-23、app/api/register/route.ts、lib/public-paths.ts:29
- **描述**：能力推导用「查不到 SpaceMember = 单用户 = OWNER」；lib/auth.ts 里改密/改邮箱/纪念日全部以 findFirst({orderBy:{id:'asc'}})（首个用户）为目标；而站点已开放注册并具备旅行圈/关注/屏蔽/举报等公开社交功能。
- **影响**：新注册用户天然是「OWNER」，可读全站审计、处理全站举报、封禁用户、改站长邮箱；再叠加 S-2 的改密端点即完成账号接管。这是**架构级矛盾**，不是单点漏洞；只修一个接口仍可走另一条链。
- **方案**：① 给 User 增加显式 role（SITE_OWNER/USER）或建 SiteMember 表，getUserCapabilities 只认该字段，删除「无成员=OWNER」；② lib/auth.ts 的「首用户」函数全部改为显式 userId 入参并标记 deprecated；③ 补两条集成测试：新注册用户所有 /api/admin/* 必须 403；用户 B 改密不得影响用户 A。

#### A-2 🟡 单实例默认值没有为扩展留出口
- **位置**：lib/infrastructure/rate-limit.ts:33（进程内 Map）、lib/cache.ts:139（进程内缓存）、lib/infrastructure/storage.ts:124-133（未配 S3 回落本地盘）、docker-compose.yml（MySQL 单实例、ffmpeg 挂宿主机）
- **描述**：限流、缓存、上传、视频转码全部是单实例假设；/api/health 只做 SELECT 1，不检查 schema 迁移/存储/队列。
- **影响**：加第二个副本即出现限流失效、缓存互相不可见、上传落到不同容器、ffmpeg 缺失；健康检查「ok」不代表可服务。
- **方案**：短期不扩副本；但把 MemoryCacheService / rateLimit 保持接口化并预留 Redis 实现（改动量很小），上传强制 S3（生产已用 COS，代码仍保留本地盘默认路径）；/api/health 增加 migrations（_prisma_migrations 未完成项）、storage（HEAD 一个对象）两项，未就绪返回 503。

#### A-3 🟡 Prisma 适配器劫持进程生命周期，优雅停机与重连是假的
- **位置**：lib/prisma-adapter.ts:136-158（构造时注册 SIGTERM/SIGINT 并 process.exit(0)）、:160-176,235（adapter 闭包按值捕获 pool）、:268-308（reconnect() 只换 this.pool）
- **描述**：收到 SIGTERM 只 pool.end() 就硬退出（in-flight 请求、上传、审计日志被切，exit code 0 掩盖故障）；reconnect() 换新 pool 但已交给 Prisma 的 adapter 仍持旧已关闭 pool（**推断**：Prisma driver-adapter 通常只 connect() 一次）。
- **影响**：每次 docker compose up -d / restart 在 in-flight 写请求上产生 502 或半写数据；DB 网络抖动后可能必须重启应用才能恢复。
- **方案**：删除适配器内 process.on/process.exit；在 lib/db.ts 导出 shutdownPrisma()，由 instrumentation.ts 的停机钩子先 server.close() 再 $disconnect()；reconnect() 改为让 connect() 返回新 adapter；compose 加 stop_grace_period: 30s 与 app healthcheck。验收：docker compose restart app 期间持续压测 0 个 5xx。

#### A-4 🟡 两代服务层并存，协议层可绕过模块层
- **位置**：lib/container.ts:1-132（10 个旧 service 单例）与 lib/modules/*（17 个领域模块）并存；18 个 API 路由直接 from '@/lib/db'（如 app/api/travels/[id]/photos/route.ts:2、app/api/images/[id]/route.ts:2）
- **描述**：新人无法判断「新接口写 modules 还是 services」；权限/可见性规则在 modules 与直连 prisma 的路由里各写一份。
- **影响**：新增一种 visibility/权限分支就漏一处；历史上「列表看不到、直链能看」正是这类分裂的产物。
- **方案**：写死一条规则——**协议层只允许 import lib/modules**；新增 lib/api/handler.ts（withAuth + zod）；18 个直连路由按领域下沉（photos/timeline → travel，images → media）；lib/services/* 标记 legacy 冻结；ESLint no-restricted-imports 禁止 app/api/** import @/lib/db，存量白名单递减。

#### A-5 🟡 跨端复用停在 lib/，展示层是「双树 + 页面内分支」
- **位置**：components/HomeClient.tsx(648) + HomeMobile.tsx(535)；app/travel 三份实现（TravelClient 323 / TravelMobileClient 288 / page 78）；详情 TravelDetailShell 489 + TravelDetailMobile 690；useIsMobile 8 个文件
- **描述**：数据获取/写入了 useApi/readWithFallback/haptics/Icon 做得不错，但业务推导与副作用层各写一遍，useIsMobile 返回 null 导致每页都要写三态样板。
- **影响**：一处规则要改 2–3 个文件（已出现相册解锁两套实现文案不一致，见 U-5）。
- **方案**：确立分工——**该合的合**（取数、写入、格式化、权限判断、图片解析），**该分的分**（视觉与手势）；抽 useTravelList()/useTravelDetail(slug) 供双端共用；提供 <MobileOnly>/<DesktopOnly> 声明式包装；**不要让桌面反向复用移动端原语**（移动端实现质量明显更高）。

#### A-6 🟢 高可用与部署架构
- **现状**：单机 Docker Compose + COS 挂载 + Nginx；MySQL 单实例；无滚动发布/多副本；mysql-data 是唯一数据副本。
- **建议**：对个人产品这是合理取舍，**不建议现在上 K8s/多副本**；但要补齐「可恢复性」：异地备份（见 E-3）、镜像 tag 回滚（见 E-5）、docker-compose.yml 的 db 加 stop_grace_period 与慢查询日志。

### 2.2 模块二 · 代码设计

**结论**：类型纪律好、单测真实；债集中在「巨型文件 + 自研基建未被使用 + 错误处理各写一套」。

#### C-1 🟡 千行文件，规则与视图耦合
- **位置**：lib/modules/travel/travel.service.ts 1083 行/34 导出；app/admin/settings/page.tsx 1076 行（内联 5 个 Tab）；app/album/page.tsx 905 行；components/album/sketchbook/Sketchbook.tsx 985 行（且已无人引用）
- **影响**：改一条规则要通读千行；CR 只能看局部；as any + 手写 DTO 映射让 schema 变更时编译器无法发现漏改。
- **方案**：travel.service.ts 拆 travel.repository.ts（查询+include 常量）/ travel.mapper.ts（纯函数，可单测）/ travel.policy.ts（权限、slug）/ 保留编排层，目标 <350 行；admin/settings 拆 5 个 Tab 组件 + hooks/use-settings-auth.ts（目标 <120 行）；app/album 抽 hooks/use-album-data.ts + AlbumModeSwitch + AlbumGalleryGrid（目标 <250 行）。验收：tsc && test 全绿，mapper/policy 新增 5–8 条单测。

#### C-2 🟡 自研取数层建好了却几乎没人用
- **位置**：lib/client/api.ts:60（apiFetch：内存缓存、并发去重、redirect:'manual' 会话失效归一）、lib/client/use-api.ts:18（AbortController 防竞态）；实测仅 8 个文件引用，89 个文件 210 处裸 fetch，全仓 AbortController 仅 6 处。
- **影响**：快速切换条目时「先发后至」覆盖新结果（app/admin/travels/page.tsx:126-151 的 fetchDetail 无 abort/reqId），后台会**改错对象**；!res.ok 静默保持旧值。
- **方案**：先迁 app/admin/**（最需要一致性），再迁 components/social/**；fetch( 由 lint 规则拦截（白名单 + 例外注释）；apiFetch 补写后失效（__resetClientCache()）；用 useApi 替换 fetchDetail 模式。

#### C-3 🟡 错误处理四套形态，116 处把 error.message 原样返回
- **位置**：118 路由中 112 有 catch、6 个无 catch；354 处 NextResponse.json({ error… })；116 处 error.message 外泄；47 处静默 catch {}；结构化 logger 仅 4 个文件引用，其余 80 处 console.error 自由文本。
- **影响**：Prisma 报错外泄表名/字段；前端靠 includes('登录') 判会话失效（lib/client/api.ts:32-37）；无 requestId，线上排查只能翻时间戳。
- **方案**：定义 ApiError(status, code, userMessage) + 单一 errorResponse() 出口；withApi(handler) 生成 requestId、记录 method/path/status/duration、异常统一 logger.error 并回写 x-request-id；前端按 code 映射；验收：grep -c "error.message" app/api 降到 < 10。

#### C-4 🟡 类型债务可量化
- **位置**：tsconfig.json 未开 noUncheckedIndexedAccess、target: es5；实测 :any 268 处、as any 93 处（travel.service.ts:131,214 的 where as any）；types/ 目录只剩一个 22 行 SQLite 声明。
- **影响**：字段改名编译器沉默；arr[0].field 在 strict 下仍是假安全（相册分页越界正是此类）。
- **方案**：CI 记录 as any 基线（93）只降不升；noUncheckedIndexedAccess 先对 lib/modules 生效；建 types/domain.ts 收敛 Travel/Memory/Media/Space DTO。

#### C-5 🟡 死代码与未使用依赖
- **位置**：components/album/sketchbook/（1086 行，0 importer）、PolaroidWall.tsx、CommentsSection.tsx、AccountSettings.tsx 均 0 importer；date-fns 源码 0 引用；typescript/postcss/autoprefixer/tailwindcss 4 个构建期工具在 dependencies（导致无法 npm prune --omit=dev）。
- **影响**：新人误改死文件；生产剪枝不可行；审计面白增。
- **方案**：单独一个 commit 删除死文件（当前 tsc + test 全绿，安全）；移除 date-fns；构建工具移 devDependencies；CI 加 report-only 未使用依赖检查。

#### C-6 🟢 状态管理与竞态
- **现状**：无全局状态库，靠 useState + 自研 hooks + useApi；乐观更新有回滚（评论点赞、收藏）；TravelImageCarousel.tsx:87-97 的 load/timeout 双触发缺幂等守卫与清理。
- **建议**：补 startedRef 幂等守卫 + 卸载清理；对跨页共享的「当前用户/能力」用 SWR 或 useSession() 单例，避免每页各取一次。

#### C-7 🟢 依赖健康

- **建议**：升级 nodemailer/mysql2，评估 next 16；audit 改阻断 + 白名单文件；启用 Dependabot（.github/dependabot.yml）。

### 2.3 模块三 · API 与数据

**结论**：API 层没有变成「路由里堆 SQL」是最大优点；但「输入校验、事务、索引、响应契约、数据演进」五项系统性缺失。

#### D-1 🟡 111/118 路由没有 schema 校验
- **位置**：仅 5 个路由引用 zod/lib/validators；65 个路由 request.json() 后手写 if；58 个路由手写 parseInt(id,10)；lib/api-response.ts:80-89 的 parseBody 直接做键拷贝。
- **影响**：mass assignment 是否危险取决于每个 service 是否恰好写了 !== undefined；类型/边界错误在协议层变成 500 或越权。
- **方案**：lib/api/handler.ts 提供 withAuth(handler) + parse(schema, body)，失败统一 422；先覆盖所有写路由（POST/PUT/PATCH/DELETE），用 codemod 生成骨架；验收：grep -L "safeParse" app/api/**/route.ts 归零。

#### D-2 🟡 多表写入无事务：全仓仅 7 处 $transaction
- **位置**：lib/modules/travel/travel.service.ts:558-585,681-690,703-753,831-834、lib/modules/social/social.service.ts:411-425；24 个文件存在 ≥2 次 prisma 写且无事务。
- **影响**：createTravel 的 ensureTravelDays 失败 → 用户得到 0 天旅行但接口返回成功；社交帖三表更新失败 → feed 标题与详情长期不一致；.catch(()=>{}) 让部分失败不可见。
- **方案**：createTravel/updateTravelInfo/deleteTravel/updateSocialPost 包 prisma.$transaction；syncTravelPost 接受 tx；逐天循环改 updateMany/批量；禁止 .catch(()=>{}) 静默同步失败（至少 console.error + 落库 lastError）。

#### D-3 🟡 索引按「字段像主键」建，不按真实查询建
- **位置**：prisma/schema.prisma:379-393 SpaceMember 只有 (spaceId,username) 唯一键与 (spaceId,role) 索引，而 access/space-scope.ts:50-54、space/permissions.ts:146-150 **每个鉴权/列表请求**都按 OR(userId, username) 查 → 全表扫描 + filesort；同类缺索引：Media.storageKey、Memory.travelId、Album.travelId。
- **影响**：单表 10 万行时鉴权路径 P95 直接劣化（每请求串行 1–3 次）。
- **方案**：加 @@index([userId, status])、@@index([username, status])、@@index([storageKey])、@@index([travelId])；上线前用 EXPLAIN 抽查这 5 条真实语句，确认 type != ALL。

#### D-4 🟡 可见性/作用域默认值危险：undefined 等于「不过滤」
- **位置**：lib/visibility.ts:10-11（scopedWhere(undefined) = {}）；调用方 app/api/anniversaries/route.ts:10 不传 userId → 匿名读全站纪念日（详见 S-13）；另有 36 处 ad-hoc visibility/isPublic 判断。
- **影响**：任何调用方漏传参数，就从「过滤」变成「全量」；这类默认值在新增接口时必被踩。
- **方案**：scopedWhere(undefined) 改为抛错，显式提供 scopedWhereAll() 迫使调用方表态；lib/modules/access 收敛剩余 36 处；补门禁测试：所有 PUBLIC_READ_PATHS 的 GET 在匿名下不得返回他人私有行。

#### D-5 🟡 响应契约不统一、幂等语义分叉
- **位置**：三种形态并存——ok() 的 {success,data}、裸对象 {posts}（app/api/travels/route.ts:51）、{error}；状态码语义漂移（app/api/memories/[id]/media/route.ts:31 把 service 异常统一映射 403）；两套点赞：/api/likes（匿名 + toggle）与 /api/social/posts/[id]/like（登录 + 确保目标态）。
- **影响**：客户端无法按状态码分流；旧点赞端点被 App 离线队列重放会「点了的赞自己消失」。
- **方案**：统一 {success, data?, error?, code?} + fail(code,status)；冻结 /api/likes（改 setLike 语义或 410）；补契约测试（同一路由的 401/404/422/500 body 形状一致）。

#### D-6 🟡 缓存：多副本失效不一致 + 无防击穿 + feed 缓存体积过大
- **位置**：lib/cache.ts:139-168（进程内 Map，tag 失效仅本进程）、lib/cache.ts:51-60（getOrSet 无 in-flight 合并）、lib/modules/social/social.service.ts:187-203（recommended feed 缓存 500 条完整帖子对象 × 用户 × 7 类型，maxSize=2000 只按条数不按字节）。
- **影响**：多副本/滚动发布时 A 写 B 旧（最多 300s）；缓存过期瞬间 N 请求同时回源；热门站内存被 feed 缓存打满。
- **方案**：feed 缓存只存 postIds+score，命中后再查库；getOrSet 加 inflight: Map<key,Promise>；多副本前切 Redis（接口已抽象）。**注**：HTTP 缓存经逐点核查**无串号**（登录态一律 private，匿名 public 但恒带 Vary: Cookie 且响应体已裁剪），这是做对的地方。

#### D-7 🟡 跨端同步协议缺幂等键、游标、删除传播
- **位置**：lib/modules/offline/sync-dispatcher.ts:113-145（POST 无幂等键、无超时）、pull-dispatcher.ts:49-121（每次全量拉，无 since）、lib/modules/offline/pull.ts:46-72（只 upsert，不处理远端已删）。
- **影响**：响应丢失即重复创建（用户看到两本同名旅行）；4xx 永久失败无限重试；Web 端删除在 App 永不消失。
- **方案**：见 P-8 与移动端 M-1/M-2/M-3，核心是 clientMutationId 幂等 + updatedSince 游标 + 墓碑列表 + 统一 /api/sync/changes 普通用户端点（不再复用 /api/admin/*）。

#### D-8 🟡 金额、时区与「墙上时间」模型不统一
- **位置**：prisma/schema.prisma:438 Travel.budget Float?（元）vs :719 Expense.amountCents Int（分）；travel.service.ts:883-894 用 Date.UTC(1970,0,1,h,m) 承载行程时刻；lib/prisma-adapter.ts:342-368 用本地 getHours() 格式化；docker-compose.yml:9 db TZ=Asia/Shanghai 而 app 未设 TZ。
- **影响**：预算与流水两套单位来回换算，漏转一处即 100 倍误差；createdAt（DB 时钟）与 updatedAt（Node 时钟）可能差 8 小时（**推断**，需在库上核对）；日期与「天」的对齐在非 UTC 部署下会错一天。
- **方案**：budget 迁移为 budgetCents（沿用现有元→分回填模式）；墙上时间改 startTimeMinutes Int；app 显式 TZ=Asia/Shanghai + adapter SET time_zone（或全链路 UTC）；CI 加集成断言「同一行 createdAt/updatedAt 差 < 5s」。

#### D-9 🟢 鉴权热路径 DB 往返偏多
- **位置**：lib/auth-middleware.ts:24-46：JWT 被验证两次 + Session.findUnique + touchLastUsed 内再一次查询；token-service.ts:127-137 活跃 token 每次查黑名单表。
- **建议**：合并为一次 verify + 一次 session 查询；Session 行加 30s 进程内缓存并在 revoke 时失效；黑名单只对疑似注销的 jti 查。

### 2.4 模块四 · 安全审计

**结论**：**这是本次评审最严重的模块。** 基础防护（XSS/上传/路径穿越/SQL/安全头/会话落库）做得比多数商业项目细，但「多用户化」没有同步收紧三处单用户假设，形成 4 条可直接利用的链。

#### S-1 🔴 相册令牌可当登录会话：匿名 → 改密 → 站长账号接管
- **位置**：lib/album-auth.ts:9-17（signSession({date, purpose:'album'})，但 signSession 只取 username/exp，实际 payload 无 username 无 sid）、lib/auth-utils.ts:12-22、lib/auth-middleware.ts:29-51（**无 sid 时跳过 DB 会话校验**）、app/api/verify-album-password/route.ts（公开路径、全文件无 rateLimit）、lib/public-paths.ts:21
- **描述**：相册令牌与登录会话共用同一 JWT 密钥与 issuer，verifyAlbumToken 不校验 purpose/audience；requireAuth 只要签名有效且无 sid 就返回 authenticated:true。攻击者把 album_token 塞进 admin_session Cookie，即成为「合法登录会话」。
- **影响**：匿名即可获得一个只校验登录的会话。若站点未设置纪念日，/api/verify-album-password 直接签发令牌；若已设置，口令是「纪念日日期」（低熵）且**无速率限制**，可在线枚举爆破。拿到会话后调用 S-2 改密端点即可接管站长账号。
- **验证（三步，只依赖公开端点）**：① curl -si -X POST https://HOST/api/verify-album-password -H 'content-type: application/json' -d '{"date":"2020-05-20"}' → 拿 Set-Cookie: album_token=…；② 用该值作为 admin_session 调 POST /api/admin/force-change-password（body {"newPassword":"Pwned123456"}）→ 当前返回 success:true；③ 以站长用户名 + 新密码登录。
- **方案**：① lib/album-auth.ts 改用独立密钥或 audience:'album' + issuer:'travel-notes-album'，verifyAlbumToken 校验 audience；② requireAuth 强制要求 payload.username 与 payload.sid，缺失即 401，删除「无 sid 跳过 DB」分支；③ /api/verify-album-password 加 IP + 全局双维度限流与失败退避，未配置纪念日时返回「未上锁」而**不签发会话级令牌**；④ 补不 mock 的集成测试：signSession({purpose:'album'}) 产出的 token 调 requireAuth 必须 401。

#### S-2 🔴 改密端点只校验登录且作用于「第一个用户」：注册即接管站长
- **位置**：app/api/admin/force-change-password/route.ts:16-37（仅 requireAuth，无旧密码、无能力位）→ lib/services/auth-service.ts:216-223 → lib/auth.ts:201-221（findFirst({orderBy:{id:'asc'}}) 改密并 revokeAllForUser）。
- **描述**：任何持有有效会话（包括 S-1 的相册令牌、或公开注册的新账号）都能改掉**全站第一个用户**的密码，同时撤销其全部会话。
- **影响**：**账号完全接管**，且站长被踢下线无法自救；全站私人内容、后台设置、成员管理尽失。
- **验证**：curl -c cj -X POST /api/register（任意用户名）→ curl -b cj -X POST /api/admin/force-change-password -d '{"newPassword":"Pwned123456"}' → 当前 success:true。
- **方案**：① **直接删除该 POST**，改密统一走 /api/admin/settings/password（旧密码 + canManageSettings），只保留 GET 供首登引导；② lib/auth.ts 所有「首用户」函数改为显式 userId；③ 测试：两用户 A/B，A 调用必须 403 且 B 密码不变。
- **止血（今天可做）**：Nginx 层 location = /api/admin/force-change-password { return 404; }（临时），或环境变量关闭注册 /api/register。

#### S-3 🔴 「无空间成员 = OWNER」：注册用户可下架/封禁他人内容、读全站审计、改站长邮箱
- **位置**：lib/modules/space/permissions.ts:153-162；app/api/admin/social/route.ts:16-59、app/api/admin/social/reports/route.ts:15-51（全站无租户过滤，动作含 TAKEDOWN_POST/HIDE_COMMENT/BAN_USER）；app/api/admin/audit/route.ts:11-16；app/api/admin/settings/bind-email/route.ts:6-32（**无能力位、无旧密码**，且 siteService.updateEmail(email, undefined, true) 不传 username → site-service.ts:16-23 回退首用户）。
- **影响**：任意注册用户可读全站审计（他人用户名/操作/IP 哈希/资源）、下架他人旅行圈内容、隐藏评论、封禁用户、篡改站长绑定邮箱（配合找回密码链路）。
- **验证**：注册后 curl /api/admin/social、/api/admin/audit、POST /api/admin/social/reports {"reportId":1,"action":"TAKEDOWN_POST"} 当前均返回成功。
- **方案**：同 A-1（显式 role / caps 默认 false）+ admin 治理接口加租户过滤/归属校验（404 语义）+ bind-email 传 authResult.username 并要求能力位/旧密码。测试：新用户 caps 全 false；report 处理非 owner 403。

#### S-4 🔴 /api/upload 写/删 IDOR：任意登录用户可给他人文章塞图、删图
- **位置**：app/api/upload/route.ts:8-66,68-95（仅 requireAuth）→ lib/services/image-service.ts:20-86（upload(postId) 只校验 post 存在，不比对 post.userId）、:88-120（delete(url) 按 imageId 直接删并回写文章 images/cover）。
- **影响**：注册用户即可向站长文章注入任意图片（内容投毒）、**不可逆删除**任意 PostImage、篡改封面。配合 S-5 先枚举再删。
- **方案**：imageService.upload/delete 增加 actor 参数并校验归属（否则 404 防探测）；或下线这条 legacy 路由（现行媒体已走 lib/modules/media/photo-upload.ts）；补不 mock 的归属测试（现有 tests/security/upload-auth.test.ts:4-10 把 requireAuth 与 service 都 mock 了，只测了 401）。

#### S-5 🔴 私有/草稿文章图片可匿名枚举（含 EXIF GPS）
- **位置**：app/api/images/[id]/route.ts:16-30（匿名按自增 id 返回 PostImage.data，无登录/归属/发布态校验，且 Cache-Control: public, max-age=31536000, immutable）；app/api/images/[id]/meta/route.ts:25-49（返回 EXIF 含 GPS）；lib/public-paths.ts:59
- **影响**：顺序遍历 /api/images/1..N 即可拉取全站历史图片，包括 published=false 的草稿与 isPublic=false 的私人文章；/meta 泄露拍摄地坐标。一旦被 CDN/浏览器缓存一年，撤回可见性也收不回。
- **方案**：路由内校验 Post.published && (isPublic || userId===当前用户)；或给 PostImage 增加随机 publicId；/meta 白名单化字段（默认不返回 gps/Make）；缓存头改 private, max-age=0。

#### S-6 🟡 会话撤销只对一半路由生效 + DB 故障 fail-open + App 会话 1 年
- **位置**：22 个 API 用 lib/current-user.ts:46-75（只 verifyToken，**不查 Session.revokedAt**）；lib/auth-middleware.ts:47-50（DB 异常 catch 后继续放行）；lib/services/auth-service.ts:42（App TTL 365 天）。
- **影响**：改密/重置密码后的「其它设备立即下线」在 /api/me/*、/api/travels/[id]/expenses 等写接口上不成立；DB 抖动时被撤销 token 复活；token 泄露窗口长达 1 年。
- **方案**：抽唯一入口 getSessionUser()（内部走 requireAuth）替换 current-user 的 JWT-only 实现；DB 异常改 fail-closed（500 + 告警）；App 会话改 30 天 + 启动静默续期 + 设备绑定。

#### S-7 🟡 X-Forwarded-For 首段可伪造 → IP 限流/登录锁定形同虚设
- **位置**：lib/request-utils.ts:2-10（取 XFF 第一段）；docs/nginx.conf.example:46（$proxy_add_x_forwarded_for 会保留客户端自带 XFF）；app/api/login/route.ts:20-22,37-60（锁定键含 IP）。
- **影响**：每个请求换一个 XFF 即绕开 login:ip/register:ip/upload:ip/reset-code:ip/danmaku:ip/search:ip 全部限制；单账号爆破被削弱为 10 次/分（login:user 仍有效）。**注**：生产 Nginx 实际配置未见，基于示例推断。
- **方案**：getClientIp 改读 X-Real-IP（Nginx 用 $remote_addr 覆盖写）或引入可信代理跳数；锁定键去掉 IP 维度、加全局滑窗；限流器迁 Redis。

#### S-8 🟡 「相册锁」是 UI 级门禁：无限流、媒体直链公开
- **位置**：app/api/verify-album-password/route.ts（无 rateLimit）、lib/album-auth.ts:14-17（不校验 purpose）、lib/public-paths.ts:32-33（/uploads、/api/uploads 公开）、app/api/uploads/[...path]/route.ts（无鉴权直出）。
- **影响**：相册只保护「列表接口」，图片本身可经直链访问；日期口令可暴力枚举。
- **方案**：限流 + 失败锁定；令牌加 albumId + 签名 URL（过期时间 + HMAC）；媒体目录 nginx 用 internal + X-Accel-Redirect（已有 UPLOAD_X_ACCEL 分支可复用）。

#### S-9 🟡 默认弱 JWT 密钥 + 只校验「非空」
- **位置**：docker-compose.yml:35-36（JWT_SECRET:-change-me-to-a-long-random-secret）、.env.example:8,11；middleware.ts:5-16、lib/services/token-service.ts:4-15 只判断非空。
- **影响**：若直接 docker compose up 而未用 scripts/docker-deploy.sh（该脚本 docker-deploy.sh:39-40 会自动生成随机密钥），密钥是公开常量 → 可离线伪造任意会话。**条件性，定 🟡；若确认某实例直接用 compose 起则等同 🔴。**
- **方案**：resolveJwtSecret 对示例/兜底串直接 throw；compose 改为强制必填语法（去掉默认值）；启动校验长度 ≥32 且非弱口令。

#### S-10 🟡 密码策略与凭证保护偏弱且不一致
- **位置**：注册/重置密码下限 6 位（lib/validators/auth.validator.ts:22-26），/admin/setup 要求 8 位（app/api/admin/setup/route.ts:37-42）；bcrypt cost 10（lib/auth-utils.ts:4-6）；/api/forgot-password/send-code 会区分「未绑定/未验证」（auth-service.ts:236-247）→ 邮箱枚举。
- **方案**：统一最小 8–10 位 + 弱口令黑名单；bcrypt cost 12；忘记密码统一返回「若已绑定将发送」；登录/注册/重置的限流锁抽成单一模块并加单测。

#### S-11 🟡 移动端安全（结论级）
- **位置**：AndroidManifest.xml:5-6（usesCleartextTraffic="true"、allowBackup="true"）、capacitor.config.ts:13-22（allowMixedContent:true、androidIsEncryption:false）、build.gradle:36-44（minifyEnabled false、缺 keystore 时回退 debug 签名）、AppUpdaterPlugin.java:127-176（下载 APK 后只校验 contentLength，无 sha256/签名校验）。
- **影响**：物理接触/备份提取可拿到明文 SQLite 与 WebView Cookie；release 可能在无 keystore 的机器上被 debug 签名（任何人可签同名同包覆盖安装）；OTA 链路被劫持可投递任意 APK。
- **方案**：加 network_security_config.xml 仅允许站点 https；allowMixedContent:false；allowBackup=false + dataExtractionRules；SQLite 开加密（密钥进 Keystore）；缺 keystore 时 throw；/api/version 下发 sha256/size/signature 并在客户端安装前校验。

#### S-12 🟡 CSRF/CORS 边界单薄
- **位置**：middleware.ts:160-180（Origin: null 与解析失败一律放行，仅靠 SameSite=Lax 兜底）、middleware.ts:74-97（凭据 CORS 按 hostname 匹配、忽略协议端口，localhost 恒在白名单）、COOKIE_SECURE 默认 false。

**结论**：动画、WebGL 生命周期、骨架屏意识都是加分项；但渲染策略（无 SSR + 双树 + 重依赖进首屏）和移动包体是最大技术债。

### 2.7 模块七 · 工程化

**结论**：CI、脚本、文档、发布手册都齐全，**但「有」与「拦得住」是两件事**。真正送上线的链路绕开全部门禁；备份与监控只写在文档里。

#### E-1 🔴 发布链路没有任何质量门禁
- **位置**：Dockerfile:10-13（SKIP_TSC=1）→ next.config.js:23,26（构建期跳过 ESLint/类型检查）；scripts/server-rebuild.sh 只做「清盘→解包→docker compose up -d --build→curl … || true」；健康检查失败仍打印「完成」，无回滚步骤。
- **影响**：任何一次「本地改完直接打包 scp 上线」都绕开 CI；类型错误/未测分支以镜像进生产；健康检查失败被当成功；出问题只能再改一版（无上一版镜像可回）。
- **方案**：① 删除 SKIP_TSC=1（内存不足用 NODE_OPTIONS=--max-old-space-size=1536）；② 部署脚本在 build 前加 npm ci && npm run typecheck && npm run lint -- --max-warnings=0 && npm test，失败 exit 1；③ curl -fsS 健康检查，失败自动回滚上一 tag 镜像；④ 每次发版打 git tag（见 E-5）。

#### E-2 🔴 CI 的四个门禁里三个「不阻断」
- **位置**：.github/workflows/ci.yml:40-66：lint（实测 **485 warnings，0 errors**，无 --max-warnings）、npm audit … || true（**43 漏洞，24 high** 全放行）、E2E 21 spec 完全不进 CI、vitest 无 coverage 配置。
- **影响**：nodemailer/mysql2/next(postcss) 等运行时依赖漏洞在任何一次 CI 都是绿色；未使用变量/显式 any 信号被忽略；UI 回归（React 渲染/竞态）零防护。
- **方案**：lint --max-warnings=485 冻结存量并每周下调；audit 去掉 || true 改阻断 + 白名单文件 + Dependabot；加 E2E job（PR 跑 5 个冒烟 spec，master 跑全量，CI 中 retries:0）；加 @vitest/coverage-v8 + thresholds {statements:60,branches:50}。

#### E-3 🔴 备份与监控只存在于文档
- **位置**：docs/DEPLOYMENT.md:140-148（要求手工加每日 2:30 备份）vs scripts/crontab.travel-notes:1-5（**只有磁盘清理，无备份条目**）；保留策略「7 天/4 周/按月」无脚本实现（migrate-database.sh 只有单次 backup/restore）；§7 告警阈值无任何实现；/api/health 的 uptime 恒为 null（STARTED_AT 从未设置）；compose 只给 db 配 healthcheck，app 没有。

## 5. 移动端专项问题（合并自移动端审计线）

> 移动端三条 🔴 与 Web/服务端同源，已并入 P0/P1 清单（M-1/M-2/M-3），此处给出细节。

#### M-1 🔴 退出登录/切换账号不清本地库、不关连接、不清缓存 → 跨账号数据可见且队列串号上传
- **位置**：app/me/settings/page.tsx:96-101（登出只 POST + push）、lib/modules/offline/native/sqlite-db.ts:240（closeOfflineDb 全仓仅被测试调用）、lib/modules/offline/travel-read.ts:52-53（WHERE deleted = 0，无 owner 作用域）、app/travel/page.tsx:29-33（在线时把本地行并入远端列表）、sync-dispatcher.ts:135-140（credentials:'include'）。
- **影响**：同机换账号后，上一个账号的旅行/回忆/照片进入 localOnly 分支直接显示；旧账号遗留 PENDING 队列项会在新账号 cookie 下 replay，把旧草稿写进新账号。
- **方案**：logout 依次 stopSyncEngine → closeOfflineDb → 清空 sync_queue/media/实体表 → 删 Directory.Data 媒体 → resetSyncQueueStorage；本地表加 ownerId/spaceId 列并在读取 SQL 加作用域，meta 表存 accountId，与当前会话不一致即整库清空；加 offline-account-switch 单测。

#### M-2 🔴 同步上传无幂等键 + 永久失败无限重试 + fetch 无超时
- **位置**：sync-dispatcher.ts:133-145（POST 无幂等键、失败只 'HTTP '+status、无 AbortSignal）、sync-engine.ts:112-122（min(retryCount,6) 只封顶指数不封顶次数；与改动记录.md:1320 自述「上限 6 次」不一致）、sync-engine.ts:53（固定 30s）。
- **影响**：响应丢失即重复创建（两本同名旅行）；任何 4xx 永久失败会被无限重试，队列只增不减；弱网下单条卡住整轮串行上传。
- **方案**：入队时生成并持久化 clientMutationId 透传，服务端按幂等键去重；4xx（除 408/429）进 DEAD 并展示服务端错误；fetch 加 AbortSignal.timeout(20s)；每轮上限 20 条；补「4xx 只试一次」「超时被中断」单测。

#### M-3 🔴 本地行与队列非原子 + 无对账 → 内容永久卡在「待同步」
- **位置**：local-write.ts:49-58（先写行后 enqueue）、media-upload.ts:150-169（文件→行→入队三步无事务）、pull.ts:52-54（syncStatus==='PENDING_UPLOAD' 直接 return false）、bootstrap.ts:16-22（启动只 start 引擎，无对账）。
- **影响**：行写入成功、入队前进程被杀，就只剩一条 PENDING_UPLOAD 行：永远不上传，且 pull 永久跳过它，UI 一直挂「待同步」。
- **方案**：行写 + 队列 INSERT 放同一事务（或先入队再写行，以队列为唯一真相源）；启动时对账补建缺失队列项；单测模拟「行写入后抛错」断言可自愈。

#### M-4 🟡 发布包零裁剪（详见 P-7）
#### M-5 🟡 本地隐私锁是空壳 + SQLite 明文 + allowBackup
- **位置**：lib/modules/offline/privacy-lock.ts:44-47（verifyPin 仅判长度且全仓无调用方）、components/offline/SyncCenter.tsx:199-207（文案承诺 PIN/生物识别 + 库加密）、capacitor.config.ts:20-22、AndroidManifest.xml:6。
- **方案**：短期在开关旁标注「开发中」或下架入口，避免虚假安全承诺；落地 getOfflineDb 加密 + 进入相册/回忆前路由守卫校验；allowBackup=false 或排除 databases/。

#### M-6 🟡 release 签名回退 debug + 版本号四处硬编码 + 移动端无 CI
- **位置**：android/app/build.gradle:4-8,17-18,40-42、scripts/build-mobile.cjs:68-70、lib/app-version.ts:5-8、scripts/verify-version.cjs（已存在但 CI 零引用）、.github/workflows/ci.yml（无 mobile job）。
- **方案**：缺 keystore.properties 时 GradleException；版本号单一来源；CI 加 mobile job（verify-version → build-mobile → cap sync → assembleRelease + artifact）。

#### M-7 🟡 OTA 无完整性校验/无灰度/无崩溃上报（同 S-11/P2-30）

#### M-8 🟡 图片上传无压缩/无断点续传/本地文件永不清理
- **位置**：media-upload.ts:68-98（2048px/q88 整图 base64 进内存）、:162-169（payload 带无用 thumbBase64）、sync-dispatcher.ts:149-181（全图 multipart 一次发）、native/filesystem.ts:40（deleteLocalFile 零生产调用）。

## 8. 结语

这个项目最稀缺的不是代码量或功能数，而是**作者对「为什么这样做」的记录与复盘习惯**——366KB 改动记录、事故复盘、真机反馈清单，这些在商业团队里都不常见。也正因为如此，本次评审才敢把话说重：**它现在最危险的地方，恰恰是它最自信的地方**——UI 与工程流程看起来「什么都有」，但真正决定安全与可恢复性的四条链路（令牌分域、权限默认值、发布门禁、数据库备份/迁移）没有闭环。

如果只能做四件事：**① 断开相册令牌与登录会话；② 删掉/加固改密端点并把权限默认值反转；③ 给部署链路加门禁并打上可回滚的 tag；④ 把数据库备份变成每天自动跑且能验证恢复的脚本。** 这四件做完，项目就从「个人可用」跨到「可以公开运营」的门槛上；其余性能与体验优化可以按 P2/P3 稳步推进。
