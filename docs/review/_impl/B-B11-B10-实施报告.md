## 2. B11 关键决策

1. **写路径按显式 username**：`updateCredentials(username, ...)` 先 `findUnique({where:{username}})`，存在→按 id 更新；不存在→创建（仅 `/api/admin/setup`、env 初始化等 bootstrap 路径）。不再 `findFirst(id asc)`，不会把操作写到别人（尤其站长）头上。
2. **删除的函数（grep 确认零调用方）**：`getCredentials` / `isRequirePasswordChange` / `updateEmail` / `setEmailVerified` / `updateAnniversaryStart` / `generateResetToken` / `verifyResetToken` / `resetPasswordWithToken` / `clearResetToken`；`forceChangePassword` 已于 P0-2 删除，本次核对。`authService.changePassword` 同步删除。
3. **保留的兼容**：`getSiteSettings()` 仍回退首用户（登录页 needsSetup、历史单管理员数据），注释明确「写路径禁止使用」。`migrateSiteSettingToUser` / `initializeDefaultAdmin` / `initializeCredentialsFromEnv` 保留为 bootstrap（仅当库里没有任何用户时动作）。
4. **忘记密码修正**：原先读「首用户的设置」——非首用户永远找不回密码，且写路径会落到首用户。现在 `findByEmail` 精确定位、`updatePasswordById` 只改该用户、`revokeAllForUser(user.username)` 只撤该用户会话。
5. **admin 页面守卫口径**：`/admin/login`、`/admin/change-password`、`/admin/setup` 豁免；未登录→登录页；首登改密→改密页；`capabilities.canManageContent === false` → `/me`；能力接口不可用（null）不踢人（接口仍会 403）。
   - ⚠️ 当前口径（P0-3）下 `canManageContent` 对**所有登录用户**为 true（「登录即可管理自己的内容」），所以正常用户不会被拦。守卫的价值是：能力收紧后自动生效 + 挡住未来无能力账号；若要现在就「普通用户不进后台壳」，需把页面守卫改用 `isOwner`/`canManageSettings` 或收紧 `canManageContent` —— 属权限模型变更（permissions.ts 不在本任务范围）。

## 3. B10 关键决策

1. **startedAt**：模块顶层 `const STARTED_AT = env.STARTED_AT || Date.now()`（env 优先兼容外部编排）。旧实现只读 env，而 compose/脚本从未注入 → uptime 永远 null。
2. **migrations**：`SELECT migration_name FROM _prisma_migrations WHERE finished_at IS NULL OR rolled_back_at IS NOT NULL LIMIT 5`。有行 → `pending`；表缺失/查询异常 → `unavailable`；否则 `ok`。
3. **storage**：用现有 storage 抽象做 **upload + delete** 探针（`health/probe-<ts>.txt`，2 字节，2.5s 超时），本地盘验证目录可写、S3/COS 验证凭证与桶权限。没有新增 `head()` 到抽象（storage.ts 不在本任务写范围），代价是每探测一次有一次 PUT+DELETE（很小对象）。
4. **503 语义**：db / migrations / storage 三者全绿才 200；任一不就绪 → 503 `degraded`。部署门禁 `server-rebuild.sh` 的 `curl -fsS` 轮询会因此拦住「半迁移的库」。
